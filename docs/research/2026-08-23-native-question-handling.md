## 1. Claude Code (`claude -p`)

### 1.1 Permission and approval machinery

- **Permission modes.** Documented table of six modes: `default` (alias `manual`), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`. Each mode defines which tool types auto-approve vs prompt. `default` prompts on first use of each tool; `dontAsk` auto-denies unless pre-approved; `bypassPermissions` skips prompts except for actions no mode auto-approves. **documented** — `/private/tmp/.../scratchpad/cc-permissions.md:60-85` (section "Permission modes").
- **Rule syntax.** Rules are `Tool` or `Tool(specifier)` with `allow`/`ask`/`deny` evaluation order deny > ask > allow. Examples: `Bash(npm run *)`, `Read(./.env)`, `WebFetch(domain:example.com)`. Bare-tool deny removes tool from model context. **documented** — `cc-permissions.md:40-50`, `cc-permissions.md:100-180`.
- **CLI spelling.** `--permission-mode <mode>` (choices: acceptEdits, auto, bypassPermissions, manual, dontAsk, plan) **observed** — `claude --help` 2026-08-23 line `--permission-mode <mode>`; **documented** — `cc-cli-reference.md:65` (row for `--permission-mode`). `--allowedTools` / `--disallowedTools` for pre-approval **documented** — `cc-cli-reference.md:44` and `cc-headless.md:160-190` (Auto-approve tools). `--dangerously-skip-permissions` / `--allow-dangerously-skip-permissions` **observed** in `claude --help`; **documented** in `cc-cli-reference.md`.
- **`--permission-prompt-tool` (headless delegation).** Spelling: `--permission-prompt-tool <MCP tool name>`. Claude Code waits for that MCP server to connect before first turn, up to `MCP_TIMEOUT` (30s default). The prompt tool cannot approve an MCP tool marked `requiresUserInteraction`; an `allow` is converted to deny (requires >=2.1.199). **documented** — `cc-cli-reference.md:110` (row for `--permission-prompt-tool`).
- **`canUseTool` (Agent SDK).** The Agent SDK exposes a `canUseTool` callback for programmatic permission decisions. The SDK overview lists Permissions as a feature linking to `/docs/en/agent-sdk/permissions`. **documented** — `cc-sdk_overview.md:34` (table row "Permissions"). Full `canUseTool` signature is **not in scraped docs**; source is silent beyond the feature table — finding: SDK docs not scraped, local package not applicable. Treat as **unverified** beyond existence.
- **`PermissionRequest` hook.** Hooks table in config reference lists events including `PermissionRequest` with matcher groups `hooks.<Event>[].hooks`. **documented** — scraped `cx-config-reference.md` analog but for Claude the hook event is listed in SDK docs; more directly, `cc-permissions.md` references "PreToolUse hook" for extending permissions. Exact hook name `PermissionRequest` appears in task prompt but scraped `cc-permissions.md` mentions `PreToolUse` hook, not `PermissionRequest` — source is **silent** on `PermissionRequest` spelling in scraped file. Observed docs do mention hooks generically. Mark `PermissionRequest` as **unverified** in this snapshot.
- **Category.** All above serve **permission / approval prompts** ("May I run X?"), not open decision questions. They gate tool execution.

### 1.2 Headless behaviour specifically (`claude -p`)

- **Non-interactive flag.** `-p` / `--print` runs one prompt and exits; not every CLI option combines with it (`--bg` rejected, `--cloud` with description rejected). **documented** — `cc-headless.md:15-25`.
- **Trust dialog skipped.** Workspace trust dialog is skipped in `-p` and when stdout is not a TTY; settings files that fail validation are silently ignored in this mode. **documented** — `claude --help` `-p` description line, and `cc-headless.md:45-55` (What runs before you trust a folder).
- **Default permission mode in `-p` is `default` (Manual) when nothing is configured.** **documented** — `cc-headless.md:300` ("built-in starting permission mode is Manual on every plan") and `cc-cli-reference.md` row for `--permission-mode` noting default.
- **When a prompt would have shown, headless does NOT hang waiting for terminal input.** It either (a) denies the tool if no pre-approval exists, or (b) delegates to `--permission-prompt-tool` if supplied, or (c) surfaces via SDK `canUseTool`. The docs say "Use `--allowedTools` to let Claude use certain tools without prompting" and describe `dontAsk` as auto-denying. **documented** — `cc-headless.md:160` (Auto-approve tools) and `cc-permissions.md:84` (`dontAsk` row). The exact fallback for plain `default` with no `--permission-prompt-tool` is **not explicitly stated** in scraped docs — inferred to be deny/skip, but mark as **unverified** (documentation is silent on the literal "what if you do nothing" case beyond telling you to pre-approve). No evidence of hanging or auto-allow.
- **SIGTERM while waiting for permission prompt:** "Waiting for an answer to a permission prompt: if you send SIGTERM ... Claude Code leaves the prompt unanswered. If your program closes the session through the Agent SDK, the SDK ends Claude Code's input before sending any signal, and Claude Code cancels the prompt as soon as the input ends." **documented** — `cc-headless.md:73-80`.

### 1.3 Is the request visible on the output stream?

- **Dedicated permission-prompt event in headless output: NO, except when delegated.** Without `--permission-prompt-tool`, a denied tool appears only as a normal `tool_result` with a denial message, not a distinct "needs approval" event. **unverified** — no scraped stream spec documents a permission event; `cc-headless.md` stream spec (system/init, hook_started, etc.) lists no permission prompt type.
- **With `--permission-prompt-tool`, the request appears as an MCP tool call in the stream.** The MCP server's prompt tool is invoked as a regular `tool_use` / `tool_result` pair in `stream-json`. **documented** — `cc-cli-reference.md:110` implies MCP tool invocation; **observed** via fixture `wt-adr/test/fixtures/harnesses/claude.ndjson` `system/init` shows `mcp_servers` array with status fields, and `cc-headless.md:226-240` describes `mcp_servers` / `mcp_server_errors` arrays in `system/init`.
- **Hook path:** `PermissionRequest` hook inputs (if exists) would appear as hook events only when `--include-hook-events` is used, but hook event shape is not documented in scraped `cc-headless.md` beyond generic hook lifecycle — **unverified**.

### 1.4 Can a caller ANSWER it without a terminal?

- **Yes, but ONLY via the permission-delegation path, not via stdin.** `--permission-prompt-tool` hands the decision to an MCP tool; the MCP server returns `allow`/`deny` and Claude continues. **documented** — `cc-cli-reference.md:110`. This works in headless (`-p`) and is the intended non-interactive answer path.
- **Agent SDK `canUseTool` callback** returns a decision programmatically; it works in headless SDK runs. **unverified** beyond feature table — `cc-sdk_overview.md:34` cites Permissions docs, not scraped.
- **No stdin protocol for answering a bare permission prompt.** Typing an answer into stdin during `claude -p` is not documented; stdin is consumed as prompt/content (10 MB cap) and piped data, not as a prompt-answer channel. **documented** — `cc-headless.md:80-100` (piped stdin handling, warning on unreadable stdin).
- **Conclusion for harness-level contract:** Permission prompts are answerable **only** through `canUseTool` or `--permission-prompt-tool` (MCP). There is no generic "write an answer to stdout/ask" channel.

### 1.5 Open decision questions — the real question

- **`AskUserQuestion` tool exists.** It is referenced as a tool name in permission docs: "`dontAsk` ... `AskUserQuestion` ... are denied even if you've allowed them" (**documented** — `cc-permissions.md:84`, `cc-headless.md:190`). It also appears in skills `disallowed-tools` example (**documented** — `cc-skills.md:330`). The tool's purpose (model asks user an arbitrary question) is implied by name but not described in scraped docs.
- **Headless behaviour for `AskUserQuestion`:** In `dontAsk` mode it is auto-denied; otherwise docs are **silent** on whether `claude -p` surfaces `AskUserQuestion` to a caller or how a caller would answer. No scraped page documents an "ask open question" stream event or callback. The `--permission-prompt-tool` explicitly **cannot** approve tools marked `requiresUserInteraction` — **documented** — `cc-cli-reference.md:110` — suggesting `AskUserQuestion` may be in that category, but AskUserQuestion's marking is **unverified**.
- **Result:** No **native** headless mechanism is documented in scraped sources by which the model can raise an arbitrary open question and have a caller answer it interactively. Permission machinery does not serve this — it gates tool execution. The only plumbings that could carry an open question are the generic MCP tool callback (`--permission-prompt-tool`) or SDK `canUseTool`, but those are typed as permission decisions, not free-form questions, and would require the model to encode the question inside a tool name/args. **Finding:** Scraped docs are silent on a native open-question protocol; the permission prompt tool is not it.

### 1.6 Exit codes and turn ends

- **Exit codes:** 0 on success, non-zero on run failure; invalid flag reported to stderr before run. Inside-run failures (e.g., missing auth) are printed as result on stdout with non-zero? **documented** — `cc-headless.md:33`. Background task termination: SIGTERM exits 143, SIGINT 130. **documented** — `cc-headless.md:71-73`.
- **Distinct exit signal for "needs input": NO.** No scraped doc lists a distinct exit code or `result` subtype meaning "stopped because it needs input." SIGTERM-while-prompt is explicitly "leaves the prompt unanswered" with no special code; resuming continues the turn (**documented** — `cc-headless.md:73-80`). Stream `result` message carries final text/cost/session metadata, not a `needs_input` cause (**documented** — `cc-headless.md:150-170` describing streaming `result`).

### 2.5 Open decision questions — the real question

Source-internal tests (`request_user_input_tests.rs:124-197`) show it emits an event awaited by a receiver, but whether that event appears on `codex exec --json` output in non-interactive mode is **unverified / silent** in docs.
- **Finding:** There **is** a native open-question mechanism (`request_user_input`) at the model-tool layer, but (a) it is experimental and gated by `experimental_request_user_input_enabled` / mode, (b) it is not documented as a headless caller-answer protocol, and (c) the harness does not expose a documented way for a headless caller to supply answers over the `codex exec --json` stream. ## 3. Pi (`pi -p` / `pi --mode json` / `pi --mode rpc`)

### 3.1 Permission and approval machinery

- **Project trust, not per-tool approval.** Pi's permission surface is about trusting project-local files/extensions, not per-command approvals. Flag `--approve` / `-a` means "Trust project-local files for this run"; `--no-approve` / `-na` means "Ignore project-local files". **observed** — `pi --help` 2026-08-23 rows `--approve, -a` and `--no-approve, -na`; **documented** — `docs/settings.md` (Project Trust section) and `pi-upstream-readme.md` (Settings / Project Trust).
- **`--no-tools` family.** `--no-tools`/`-nt`, `--no-builtin-tools`/`-nbt`, `--tools`/`-t <list>`, `--exclude-tools`/`-xt <list>` control which tools are available. No per-invocation "ask before bash" gate akin to Claude/Codex. **observed** — `pi --help`.
- **Extension-driven gates.** Extensions subscribe to `tool_call` event and may return `{ block: true, reason }` after prompting the user via `ctx.ui.confirm`/`select`. Example: `pi.on("tool_call", async (event, ctx) => { const ok = await ctx.ui.confirm(...) })`. **documented** — `docs/extensions.md` Quick Start example and Events section (`tool_call (can block)`).
- **Category.** `--approve` is a trust prompt (permission-like), while `ctx.ui.confirm` is a permission prompt built by extensions, not baked into the core harness. Both gate tool execution, not open questions.

### 3.2 Headless behaviour specifically (`pi -p`, `--mode json`, `--mode rpc`)

- **Non-interactive modes do not show trust prompt.** "Non-interactive modes (`-p`, `--mode json`, `--mode rpc`) do not show a trust prompt. Without an applicable saved trust decision, they use `defaultProjectTrust` from global settings: `ask` (default) and `never` ignore those project resources, while `always` trusts them. Pass `--approve`/`--no-approve` to override." **documented** — `docs/settings.md` (Project Trust) and `dist/cli/args.js` help.
- **Tool availability in headless.** If a tool call would have been gated by an extension `confirm` dialog, in `-p`/`json` the UI helper `ctx.ui.confirm` has `hasUI == false`. Extensions are expected to guard with `ctx.hasUI` before prompting. **documented** — `docs/extensions.md` (`project_trust` handler notes `ctx.hasUI` limited context; Mode Behavior notes `true` in TUI and RPC modes, `false` in print mode (`-p`) and JSON mode). Concrete consequence is **undocumented**: whether blocked tools auto-deny or auto-allow in print mode when extension returns no decision — **silent / unverified**.
- **RPC mode is the intended headless interactive surface.** `pi --mode rpc` keeps the agent alive over stdin/stdout JSONL and supports steering/follow-ups. **documented** — `docs/rpc.md:1-20`. This is the harness's analogue to a headless caller channel.

### 3.3 Is the request visible on the output stream?

- **Print mode (`-p`):** Output is the final response text (or with `--mode json`, a stream of session events). No dedicated permission prompt line is documented. Trust decisions appear only as startup diagnostics, not as a turn-blocking event. **unverified** — no doc describes a visible prompt object in `-p` output.
- **JSON mode:** Emits `JsonAgentSessionEvent` stream (documented in `docs/json.md`). Event types include `agent_start/end`, `turn_start/end`, `message_start/update/end`, `tool_execution_*`, but no `permission_request` event is listed in scraped docs. **documented via docs/json.md** — header lists event types, none is permission.
- **RPC mode:** Events are streamed, and extension UI methods have an RPC protocol (e.g., `select_request`/`select_response`). The extension docs note `ctx.ui.confirm` has a wired RPC path. **documented** — `docs/extensions.md:900-950` notes `true` in TUI and RPC modes, references `rpc.md#extension-ui-protocol`.

### 3.4 Can a caller ANSWER it without a terminal?

- **Print mode (`-p`): NO.** No callback or stdin protocol for answering a trust/approval prompt. Override is only via CLI flags `--approve`/`--no-approve`. **documented** — `docs/settings.md` (pass `--approve` to override).
- **RPC mode: YES, but only for extension UI dialogs, not core trust.** Extensions that call `ctx.ui.select`/`confirm`/`input` in RPC mode trigger a JSON request the RPC client answers with a response object (see `rpc.md` Extension UI Protocol). Trust prompts via `project_trust` also use `ctx.ui.confirm` and could be answered there — **documented** — `docs/extensions.md` (`project_trust` handler returning `{ trusted: "yes" }` via UI).
- **Conclusion:** Permission-scale prompts are answerable **only** in `pi --mode rpc` via the RPC UI protocol, not in `pi -p`.

### 3.5 Open decision questions — the real question

- **No built-in `ask_question` / `request_user_input` tool.** Pi ships with four built-in tools: `read`, `write`, `edit`, `bash`. No `ask_question`, `AskUserQuestion`, or `request_user_input` tool exists in core. **observed** — `pi --help` lists no such tool; **documented** — `pi-upstream-readme.md` Quick Start ("By default, pi gives the model four tools: `read`, `write`, `edit`, and `bash`").
- **Open questions are extension-defined.** Extensions may register a custom tool (e.g., `pi.registerTool({ name: "ask_question", ... })`) that uses `ctx.ui.select`/`confirm`/`custom()` to pose structured questions. The upstream `ask_question` or `request_permissions` patterns are not in core. **documented** — `docs/extensions.md` Custom Tools section.
- **Headless answerability of open questions:** Same as above — only `pi --mode rpc` carries UI dialogs over the wire; `pi -p` / `--mode json` have no interactive answer channel. In print/json, `ctx.ui.select` would see `hasUI==false` and extensions must choose a default or block. **documented** — `docs/extensions.md` Mode Behavior note.
- **Finding:** No **native** harness-provided open-question mechanism exists in pi core. The harness provides the RPC extension UI plumbing that third parties can build on, but the question tool itself must be supplied by an extension.

### 3.6 Exit codes and turn ends

- **Exit codes not documented in scraped docs.** `pi --help` does not list exit codes; `docs/json.md` / `docs/rpc.md` are silent on a distinct "awaiting-input" code. The help text does not mention `awaiting-input`. **Finding:** No distinct exit code or stream cause meaning "stopped because it needs input" is documented.

### 4.3 Is the request visible on the output stream?

- **JSONL event stream.** `muse exec --json` emits machine-readable JSONL events on stdout. **observed** — `muse exec --help` `--json` row; **documented** — `muse-extending.html:179-190` (Headless and CI: `muse exec --json`).
- **Specific permission visibility not documented in scraped pages.** `muse-permissions.html` and `muse-extending.html` do not enumerate permission prompt events in JSONL. The interactive clarifier UI is described (`muse-interactive.html:187` clarifying questions), but its JSONL representation is not scraped. **Finding:** Docs are silent on whether an approval hold appears as a distinct JSONL event in `muse exec --json`.
- **Open-question visibility:** Clarifying questions are described for interactive TUI (pause turn, show 1-3 questions with options, pick with number keys/Space/Tab, Enter submits) — **documented** — `muse-interactive.html:187-196`. No scraped doc confirms the JSONL shape for these in headless.

### 4.4 Can a caller ANSWER it without a terminal?

- **Permissions: NO documented programmatic answer path in headless.** No `--permission-prompt-tool` or `canUseTool` callback is listed for Muse Code. Execution policy is set at launch (`--disable-approval`, `--yolo`, trust). **observed** via help; **documented** via `muse-configuration.html` flag split. No hook or MCP callback for approvals is in scraped docs.
- **Open questions: YES, via `request_user_input` tool + headless flag.** `muse exec --help` documents `--user-input-auto-resolve` as the headless handler for `request_user_input`. The interactive clarifier is answerable in TUI with keyboard; in headless the flag presumably auto-resolves or auto-cancels. **observed** — `muse exec --help`; docs for the tool itself not scraped. The SDK/entry does not document a caller-supplied answer channel over JSONL stdin — **silent**.
- **Conclusion:** Permission prompts are **not** answerable programmatically in `muse exec` without pre-configuring policy. Open questions have a headless knob (`--user-input-auto-resolve`) but not a documented answer-injection protocol.

### 4.5 Open decision questions — the real question

- **`request_user_input` tool exists (and possibly `AskUserQuestion` alias).** `muse exec --help` references `--user-input-auto-resolve` with "Offer request_user_input and auto-cancel prompts (headless)" — direct evidence the tool exists. **observed** — `muse exec --help` 2026-08-23. The interactive docs describe an equivalent native UI: "When the agent asks you a question — clarifying questions: one to three, each with a few options, single- or multi-select" (**documented** — `muse-interactive.html:187-196`). This is the user-facing manifestation of `request_user_input`.
- **Headless handling:** Interactive clarifiers pause the turn and show options; headless `muse exec` with `--user-input-auto-resolve` presumably resolves them automatically (observed flag description). Whether a headless caller can inject arbitrary answers through a native question/answer channel (like a callback or stdin JSON) is **not documented** in scraped `muse-extending.html`. The flag's wording "auto-cancel prompts" suggests the default headless behavior is to **deny/skip** open questions, not to surface them. **Finding:** Native open-question mechanism **exists** in Muse Code (clarifying questions / `request_user_input`), is **interactive-first**, and has no documented headless answer protocol beyond auto-resolve/cancel.
- **Distinction:** This is the one harness where the permission machinery and the open-question machinery are **explicitly separated**: approvals gate shell/file side effects; clarifying questions gate decisions about what to do next. The docs consistently keep them distinct (approval modes vs clarify section).

### 4.6 Exit codes and turn ends

- **Exit codes reflect how the run ended, not whether work is correct:** `0` when turn completes, `1` when it fails or is cancelled (including `--max-model-steps` limit), `2` for usage error, `130`/`143` for SIGINT/SIGTERM. An agent can finish turn and still report failing tests, yet exit `0`; gate on your own test command. **documented** — `muse-extending.html:189` (Headless and CI — `muse exec prints ... exit code` paragraph, scraped via `muse-extending.html` raw grep: line ~189).
- **Distinct exit signal for "needs input": NO documented.** No row defines an "awaiting-input" code. `1` covers generic failures/cancellations including step limit, but not a distinct needs-input cause. **documented** — `muse-extending.html:189` list is exhaustive and omits such a cause. `130`/`143` are POSIX signals, not hcn's `awaiting-input`.

## Open

All four harnesses treat permission prompts and open decision questions as distinct, but none documents a complete native open-question/answer loop for headless.

- **Permission prompts** have first-class, documented headless story in two harnesses (claude via `--permission-prompt-tool`/`canUseTool`, codex via config/granular, muse via launch flags, pi via `--approve` + RPC UI) — each with exact spelling.
- **Open decision questions** have varying native presence:
  - **claude** — `AskUserQuestion` exists as a tool but its headless surfacing/answering is **not documented** in scraped `-p` docs; permission prompt tool cannot approve `requiresUserInteraction` tools, hinting it may not carry this — **no native mechanism demonstrated**.
  - **codex** — `request_user_input` exists natively (1-3 questions, tool schema, mode-gated, experimental) but caller-answer in `codex exec --json` is **not documented** — experimental flag plus source-level tests describe mode gating and blocking semantics, not a headless protocol.
  - **pi** — **no native** harness-provided question tool; four core tools only. Open questions must be built as extension custom tools and are answerable only in `pi --mode rpc`, not `pi -p`.
  - **muse** — **native** clarifying question UI (1-3 questions, interactive TUI) and implicit `request_user_input` tool (evidenced by `--user-input-auto-resolve`), but headless handle is auto-resolve/cancel, not a caller-answer loop.

Where a source does not address a question, the entry above says "silent" / "unverified" — that is a finding, not a gap to fill.
