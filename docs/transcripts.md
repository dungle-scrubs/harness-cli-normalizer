# Native transcripts

Use `hcn inspect <harness> --transcript` to inspect passive read methods and their evidence. Use `hcn transcript read` to export one native conversation as JSONL, and `hcn transcript ls` to list the saved sessions. These commands do not resume a model, load instructions or extensions, or modify native history, and they write nothing to a native store.

```sh
hcn inspect pi --transcript
hcn transcript read pi --file /path/to/native.jsonl > transcript.jsonl
hcn transcript read pi --id NATIVE_ID --cwd /path/to/project --limit 100
hcn transcript read pi --file /path/to/native.jsonl --since OPAQUE_BOOKMARK --limit 100
```

`hcn transcript ls` lists the saved native sessions each harness kept, newest first, without resuming or reading one.

```sh
hcn transcript ls
hcn transcript ls --all-workspaces --limit 20
hcn transcript ls --cwd /path/to/project --headless --harness claude,codex
```

It walks each native store on the call and computes the rows from it. There is no index, no cache and no persistent state, and the walk grows with the store. Stdout is JSONL: one `session-list-source` header, one `session` row per saved session, one `session-list-result`. A row carries `harness`, `id`, `file`, `cwd`, `lastWriteAt`, `startedAt`, `sizeBytes`, `mode`, `readable` and `blocked`; its `id` and `file` are what `transcript read --id` and `--file` accept, and `readable` says whether a verified read method addresses that source. `--cwd` admits only the sessions whose workspace is exactly that directory and defaults to the invocation directory; `--all-workspaces` drops the filter and cannot be combined with `--cwd`. Headless runs are omitted unless `--headless` is given.

`--limit` truncates the rows the call prints. It does not reduce the walk: every store is walked, every row is built, and the whole set is sorted before the limit applies, so a limited call costs what an unlimited one costs. `more` in the result says rows existed beyond the limit. There is no continuation token and no cursor, so a consumer that needs the rest re-runs without `--limit` and pages the listing itself. Rows are ordered `lastWriteAt` descending, then `harness` ascending, then `id` ascending; that triple is the whole order, including for rows that share a `lastWriteAt`.

`lastWriteAt` is the last native write to the source, as the filesystem reports it. It is the sort key because it is the one time every store can produce, not because it is the best time available: `rsync`, a `git checkout`, a backup restore or a sync client rewrites it without a byte of the conversation changing.

`startedAt` is what the native header itself says, or null where the store records none. Each store names it differently and hcn reports them all as `YYYY-MM-DDTHH:MM:SS.mmmZ`: Claude takes the first record carrying a `timestamp`, since a transcript opens with settings records that carry none; Codex takes the record-level `timestamp` on `session_meta`; Pi takes `timestamp` on the v3 session header; Muse takes `recorded_at` on the first payload record, counted in microseconds since the epoch; Cursor takes `createdAtMs` from the `meta.json` the listing already opens, counted in milliseconds; Antigravity takes `created_at` on the first step of its log, which it writes at second precision. A header time that names an offset rather than `Z`, or that falls outside a four-digit year, reports null rather than being read as UTC. `lastWriteAt` is never substituted for a missing `startedAt`, and rows are not sorted on `startedAt`, because a store can leave it null.

`sizeBytes` is the row's own native source, from the stat the walk already takes, so it costs nothing extra on any harness. It is the row's file rather than whichever file its markers came from: Cursor reads `meta.json` for the workspace and reports the `store.db` beside it. It tells a consumer what a `transcript read` of that row would have to get through, which is not a small question - the largest Codex rollout on this machine is 1.25 GB and `transcript read --limit 1` against it takes 4.6 s. There is no record count: only Antigravity's index carries one, and estimating one from bytes would be a guess.

Two counts in the stream are easy to confuse. A harness's `rows` in the result is what that harness contributed after the workspace and headless filters and before `--limit`. The result's `rowsReturned` is what was actually printed. Under `--all-workspaces --limit 5` on this machine, `rowsReturned` reads 5 beside per-harness `rows` of 852, 1914, 1313, 990, 72 and 31. `matched` would be the clearer name for the per-harness count; renaming a published wire field is breaking, so it waits for a release that is already breaking for another reason.

`readable` and `blocked` answer two different questions. `readable` says a verified read method addresses this source shape; it does not say the read will succeed. `blocked` names the cheap precondition a read would refuse on right now, as `{ issue, reason }`, or null. The check is the one the read itself makes: each reader declares the sibling files it needs quiet, and the listing stats them. Cursor declares `store.db-wal` and `store.db-journal`, so a chat with a turn in progress lists `readable: true` with `blocked.issue` `guarantee-unmet`, and a consumer can skip a read that is already known to refuse. No other harness declares a sibling, so no other harness pays for the check; on this machine it costs about 30 ms across 72 Cursor rows.

`blocked: null` is not a promise. It means no cheap check this listing could make was observed to fail: a sibling that could not be stat'd leaves the answer null, the source is checked at the path the walk found rather than through a symlink the read would resolve first, and a native session can open between the listing and the read. Preconditions that are not cheap stay where they are - a Claude or Muse read needs a filesystem clone, and an Antigravity step log with `truncated_fields` is refused only once the log has been read.

`mode` is `interactive`, `headless`, or `unknown` where the store carries no marker; a consumer treats `unknown` as interactive unless it knows better. Claude reads `entrypoint` (`cli` against the `sdk-` callers) and Codex reads `session_meta` `source`/`originator` (`exec` and `codex_exec` are headless). Pi, Muse, Cursor and Antigravity carry no observed marker, so their rows report `unknown`. Child conversations are not rows: Claude sidechains, Codex spawned agent threads, Muse `subagent/` sessions and Antigravity nested conversations. A row whose store names no workspace reports `cwd: null` and appears only under `--all-workspaces`.

Each harness that was asked for is reported in the result with its state. `divergent` is a harness with no listing method and `failed` is one whose store could not be read; both carry the reason, the exit code stays 0, and the status reads `partial` so a consumer can report the coverage gap. Invalid arguments refuse with exit 2, as `transcript read` does. Cursor's workspace comes from the `meta.json` beside each chat store, never from the store's own meta row, which holds credential fields. Antigravity's workspace comes from `conversation_summaries.db` beside the `brain` directory, read through the same passive filesystem clone the readers use; that index names a workspace only for the conversations it recorded one for.

The file path identifies a native conversation. It is not an HCN capture or consumer ID. Pi ID lookup uses the selected workspace's native session directory under `PI_CODING_AGENT_DIR`, or `~/.pi/agent`. An explicit file is useful for native custom session directories. Missing sources fail; HCN never creates them. Codex ID lookup searches exact native filenames under CODEX_HOME/sessions and CODEX_HOME/archived_sessions (default ~/.codex). Database-only or renamed locations require an explicit file. Inherited storage still resolves within CODEX_HOME. Referenced attachments and separate parent/child conversations stay references. A Codex history_base is an explicit bounded storage range, not permission to export the rest of that parent conversation.

The stream contains one `source`, zero or more `record` objects, and one terminal `result`. A batch succeeds only when `result.status` is `complete` and the producer exits 0. Invalid requests and descriptor refusals exit 2; read, cleanup, interruption, and output failures exit 1. Records are provisional until success. Broken pipes do not establish successful exports.

Each record retains its complete native `original` object alongside normalized message parts, tool identifiers, timestamps, and established relationships. Unknown native fields stay in `original`; unfamiliar entry kinds and links stay unknown. Native IDs can be null. Positions are source coordinates, not permanent HCN IDs. Use a lossless JSON parser or retain the original wire text when preserving native numbers beyond JavaScript's exact range. Plain `JSON.parse` can round them.

Coverage describes the accessible retained history, including saved branches and pre-compaction entries. `--limit` counts whole native entries in one finite view. It does not limit bytes or validation work. Current context is not substituted for retained history. `historicalLoss` separately describes established native persistence omissions; complete retained coverage does not reconstruct deleted or never-persisted events.

Save a returned bookmark only after successful delivery. Send it back unchanged through `--since`. HCN verifies the native identity and the entire committed prefix. Empty and EOF reads can return usable same-boundary bookmarks. Earlier edits, truncation, incompatible methods, or an unknown bookmark version fail rather than silently restarting. Caller-supplied relocation can work when identity and the prefix still match. HCN keeps no bookmark registry, index, watcher, retention policy, or search service.

## File consistency and custom harnesses

Pi and Codex rely on their identified native append-only write protocols. They capture a regular file's device/inode identity and finite size, read the same prefix twice through one open handle (the verification pass uses bounded chunks), compare every byte, and verify path/handle identity and absence of truncation. Later appends are outside that view. Only LF-complete entries are parsed; an unfinished final framing unit is reported with its position and excluded from progress. Required consistency checks are reported individually. All file closes start together and share one one-second cleanup bound. For multi-source histories, every captured prefix is rechecked after all contributing sources have been captured.

Claude, Muse, Cursor and Antigravity instead read a private filesystem clone through HCN's packaged helper. They do not assume append-only persistence. The clone fixes one byte view, which can occur between native writes; it does not promise a complete native transaction. macOS and Linux require compatible clone-capable source and temporary storage. No ordinary copy is substituted. The helper has a five-second acquisition deadline and one-second cleanup bound. The clone is removed before successful completion. See [platforms, packaging and observed evidence](transcript-snapshot.md).

Cursor stores are SQLite databases in write-ahead-log mode. During a turn, committed writes sit in `store.db-wal` and the main file lacks them. HCN therefore requires the WAL and any rollback journal to be absent or empty before the clone and after the read. Cursor checkpoints and removes the WAL when the turn ends. A pure TypeScript page reader then reads the cloned main file; no SQLite engine opens the native store, so no checkpoint, recovery or lock can touch it. The reader projects the latest root's message list onto one JSON line per message, and bookmarks and positions refer to that projected view. The WAL checks cannot exclude a checkpoint that starts and ends inside the clone window. Every blob is content-addressed, so HCN verifies each blob's SHA-256 against its ID and resolves every root reference; a view that mixes page versions fails. A symlinked `store.db` is resolved first, so the WAL checks apply to the real file. Blob IDs address content, not occurrences: a repeated identical message appears twice with the same `nativeId`, and positions tell the occurrences apart.

The checks detect observed replacement, truncation, and prefix edits. They are not a filesystem snapshot against arbitrary in-place writers that can change bytes and restore them between observations. The native writer assumptions are part of applicability, not a waived coverage limit. Customized Pi qualifies only while preserving the v3 one-file conversation, native identity, append/order/framing, and saved selection semantics. Unknown extra fields and entry kinds are preserved; identical version labels alone do not establish arbitrary custom lifecycle behavior.

A from-scratch harness needs its own immutable descriptor facts, passive lifecycle, source assembly/order rules, native identity rules, normalization mappings, and synthetic conformance evidence before a method is enabled. Existing HCN does not provide a runtime harness-registration or custom-reader plugin API. A consumer owns its native-format extensions until they meet that contract. `--accept-limits` cannot waive passivity, integrity, identity, consistency, or requested bookmark/paging behavior.

## Verification and limits

All added tests use synthetic histories. The CLI tests cover inspection/refusals, full Pi export, ID lookup, bounded continuation, retained branches/tool results, Codex legacy and inherited export, archive lookup, invalid cutoffs/identity/cycles, incomplete initialization, and output failure. Injected filesystem/clock/output tests cover interruption, bounded cleanup, in-call changes, and emission interruption. Conformance tests cover empty/EOF bookmarks, incomplete UTF-8 tails, corruption and duplicate keys, exact numbers/Unicode, and input validation. Method-selection tests cover unwaivable passivity, unavailable retrieval, preference for full history, and explicit reduced-view opt-ins.

The tests read no private native transcript. Cursor and Antigravity evidence also includes structural observation of local stores written by hcn's own runs; see [their evidence](transcript-evidence.md#cursor-20260915-d2fe57e). These tests verify HCN's reader behavior; pinned native source supplies documented writer evidence. They do not claim an observed live native writer experiment.

Cursor tests build synthetic stores with the running runtime's own SQLite engine (`node:sqlite` under Vitest, `bun:sqlite` under `bun test`), including overflow pages and multi-level b-trees. They cover ordering, exact originals, withheld encryption keys, earlier-root prefix failures, schema refusals, ID lookup, continuation across an appended turn, rewritten-prefix refusal and the nonempty-WAL refusal. Antigravity tests cover step normalization, contiguity and truncation refusals, path identity, ID lookup and continuation across appended steps.

Claude and Muse synthetic CLI tests cover native-file reads, ID lookup and ambiguity, snapshots, exact originals, tool mappings and continuation across appends or rewrites. Helper tests cover clone independence, missing/nonregular sources, deadlines and interruption. These are synthetic reader checks, not real private transcript reads. Codex compressed storage and database-only ID resolution remain unsupported. No Trevor ownership ticket is changed.

The current file pipeline retains buffers for contributing source ranges and parsed originals, uses bounded verification chunks, and hashes each committed byte once per read. It uses memory proportional to source size and revalidates the full prefix even for small batches. Whole native entries are never truncated to fit memory. A large-source read can fail with `source-inaccessible` if allocation or I/O cannot complete. Streaming validation can reduce peak memory without changing the wire contract.

Review dispositions: the selected Pi implementation writes `branch_summary.fromId` from the same branch origin used for `parentId`; a differing pair is outside that verified mapping, so it remains original data with an unknown normalized origin. File compatibility is conditional on the declared native format/write protocol, not authentication of an arbitrary custom writer. See the method applicability before using a modified writer.
