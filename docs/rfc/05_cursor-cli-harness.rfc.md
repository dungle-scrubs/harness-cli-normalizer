# RFC-05: Cursor CLI harness

## Abstract

hcn drives four harness CLIs through one surface, and ROADMAP.md names Cursor CLI as the next harness to add. This RFC specifies the `cursor` descriptor for Cursor CLI `agent` version 2026.09.10-fd3934a, the mapping from its `stream-json` events onto hcn's `HarnessEvent` vocabulary, a new typed `trust-refused` failure class for its workspace-trust gate, and an effort mechanism that resolves model plus effort to an existing model slug. Every value is grounded in the logged-in capture spike; v1 covers one-shot headless turns plus resume, while persistent sessions, transcripts, and session listings stay out.

## Introduction

### Problem statement

Callers that drive coding-agent CLIs through hcn cannot reach Cursor CLI today. Each harness difference Cursor introduces (harness-minted identity with no caller-assigned id flag, a trust gate that refuses untrusted workspaces, effort expressed as model-slug suffixes, resume that creates on missing ids, two store roots keyed by different slug rules) would otherwise be handled ad hoc by every consumer. hcn exists so that translation lives once, in descriptors and pure readers, behind the stable `HarnessEvent`, exit-code, and refusal contracts.

### Scope

In scope: the `cursor` descriptor with every field value and its probe evidence; the `stream-json` decoding table; failure classification including the new trust-refusal class; resume semantics under `onMissing: "create"` and the resume-guard consequences; the refusal surface (`--tools` / `--exclude-tools`, effort without a matching slug, session mode, stale resume ids); the effort-as-slug mechanism; fixtures and tests; rollout (`verifiedAgainst`, smoke tripwires, skill update).

Out of scope, each with its reason:

- **Persistent headless sessions (ACP).** Cursor answers approvals and questions only over `agent acp`, and hcn has no ACP support (`SESSION_INPUT_KINDS` and `NATIVE_APPROVAL_PROTOCOLS` have no ACP member). Owner decision: v1 ships one-shot turns plus resume only.
- **Native approvals.** Same reason: without ACP there is no channel to answer; denied calls and rejected questions surface as data (structured non-terminal error events, exit 0), never as prompts.
- **Transcripts and session/transcript listing and reading.** Owner decision: out of v1 until the on-disk layouts are confirmed. The descriptor carries `transcript: null`, so transcript reads report divergence through the existing path. (Superseded for transcript reading: the `cursor-store-v1` method reads the native `chats/<md5>/<id>/store.db` chat store, so `transcript` no longer carries `null`. Session and transcript *listing* stays out of v1.) (Superseded for transcript listing: `hcn transcript ls` lists saved sessions across the harnesses, cursor included, computing the rows from the native stores on each call; issue #202. Session listing stays out.) `hcn ls` lists descriptors (one line per harness from `SHARED_DESCRIPTORS`), not sessions, so cursor appearing in `hcn ls` output is intended and is not the excluded listing.
- **Depending on hidden flags.** `--new-session-id` exists but is undocumented; hcn MUST NOT use it. Identity stays harness-minted.
- **Passing `--trust` by default, or through passthrough.** hcn never passes `--trust`: it persists `.workspace-trusted` beyond the process, and only the caller's explicit opt-in may own that state. Passthrough cannot carry it either: tokens after hcn's bare `--` separator join Cursor's positional prompt (probes 40/41), so `--trust` after `--` becomes prompt text and the gate still refuses. A caller that wants `--trust` invokes `agent` outside hcn. hcn autonomy maps to `--force`, which bypasses the gate per run without persisting. Non-empty passthrough on cursor refuses before spawn (see Passthrough): no passthrough token ever reaches Cursor as a flag.
- **Native terminal resume (`hcn interactive`).** Out of v1. The existing preflight refuses it: `INTERACTIVE_INTERFACES` has no cursor entry, so the request ends `unsupported-interface` before any spawn.
- **Auto-update.** No documented off switch exists (spike Q11). hcn leaves it alone and records it as a drift risk.
- **Grok Build.** Deferred for lack of a subscription; it stays on ROADMAP.md as blocked.
- **`--mode plan|ask`, `--approve-mcps`, `--workspace` extras.** Plan/ask modes and MCP approval have no `TurnOptionKey` to ride; `--workspace` targeting is the spawner's job, as on codex. There is deliberately no guard on `--workspace` (or `--add-dir`) in passthrough: those tokens join the prompt as text (see Passthrough) and never reach Cursor as flags, so the session files under the spawn cwd and the guard's path stays correct.

### Fit of this revision

The users are the owner's consumers (delegation workers and similar) that run coding-agent CLIs through one surface and need Cursor runs alongside the existing four. hcn normalizes harness interfaces and supervises the processes it starts. Every capability below either expresses a Cursor difference in hcn's existing vocabulary (descriptor, decoder, failure naming, divergence reporting), which **holds** the scope, or supervises one spawned process (resume guard, stdin close, retryable policy), which the scope test permits. The widening (a fifth harness, a fifth set of users on Cursor) is the owner's settled decision, recorded on ROADMAP.md. Declined candidates (ACP sessions, transcripts, trust-by-default, auto-update control) leave their record here, in the scope boundaries above, as the fit-check discipline requires.

### Errata (2026-09-17; status stays Accepted)

1. Config-tier sandbox and access values refuse, not diverge. The Refusals row says non-arg-tier sandbox values diverge with tier-and-key provenance, and the Sandbox section says profile and config-tier sandbox values diverge through the no-spec split. The code refuses user-config and project-config values of both options with `unsupported-option` (verified: project-config `sandbox: read-only`, user-config `sandbox: read-only`, and project-config `access: read` all refuse). Only the profile-tier default diverges (sandbox; access has no profile tier, so every access value refuses). Refusal fails safe, so the spec text is corrected to the code, not the other way around.

2. The plan-turn resolve step also runs when a model is present without effort. The Composition site paragraph says the step runs when arg-tier `--effort` is present; the code also runs it when a model from any tier is present without effort (verified: `--model claude-opus-4-8` with no effort refuses `unknown-model` with the stem's 5 row slugs, and `--model claude-opus-4-8-high` with no effort leaves argv and provenance unchanged). A bare stem refuses with its row instead of reaching turnTail's full-list `unknown-model`.

3. Passthrough does not join the prompt. Probes 40 and 41 rendered hcn's own bare `--` into the `agent` argv, and `agent` treated every token after that separator as prompt text. That was the separator, not the CLI. Rendered without `--` after hcn's argv, a real flag takes effect (`--model gpt-5-mini` switched the model) and a bogus flag fails natively with `unknown option`, on launch and resume (2026-09-17, agent 2026.09.15-d2fe57e). Cursor now declares `launch.passthrough: "after-argv"` like the other four harnesses, and a non-empty tail no longer refuses. ADR 0003 records the root cause.

### Context

This RFC follows the same house pattern as the four existing descriptors: facts as data in `src/knowledge/cursor.ts`, translation in `src/interpretation`, lifecycle in `src/execution`. It creates no new layer and changes no existing harness behavior. RFC-02's rules apply throughout: no new branch on `h.name`, one owner per rule, and every closed vocabulary declared once as a runtime array.

## Terminology

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119.

| Term | Meaning |
| --- | --- |
| Harness | One coding-agent CLI hcn drives. This RFC adds `cursor` (bin `agent`) to `claude`, `codex`, `pi`, `muse`. |
| Descriptor | The immutable data describing one harness (`src/knowledge/cursor.ts`), per CONTEXT.md. |
| Slug | A model id as Cursor spells it on `--model` (for example `composer-2.5-fast`). Slugs are opaque strings; hcn never parses structure out of them, except for the Stem rule below, which derives table keys mechanically and synthesizes no slug. |
| Family | One named row of the `effortSlugs` table, keyed by stem (for example `claude-opus-4-8`, `gpt-5.2`, `kimi-k3`). Membership is enumeration, never derivation: each row lists exact hcn-effort-word to slug pairs transcribed from `out/models.txt` at `verifiedAgainst` (addendum F). A stem whose bare form is itself a slug maps it to the tier the init display reports: `medium` for `gpt-5.2`, `gpt-5.1`, `gpt-5.3-codex` (probes 29/48/49). Stems with no bare slug (`claude-opus-4-8`) are keys only and are never valid `--model` values. Each `thinking` form is its own stem with its own effort row (see Stem rule below), never an extra entry in the plain row. `-fast` twins are NOT row members: `-fast` marks a speed variant of one listed slug (70 twins, zero orphans, but 83 of the 153 non-fast slugs have no twin at all, addendum I), and it is handled by the idempotence check in Resolution rules, never by composition. Bare-only stems with no effort siblings (`auto`, `composer-2.5`, `claude-4.5-sonnet`, `claude-4-sonnet`, `gemini-3.1-pro`, `gemini-3-flash`, `gemini-3.5-flash`, `gpt-5-mini`, `kimi-k2.7-code`) are complete selections by themselves and take no `--effort`. |
| Stem rule | The mechanical rule that derives every `(stem, effort[, fast])` key from a slug in `models.txt`, applied in order: (1) strip one trailing `-fast` and record the fast flag; (2) if the remainder is `<S>-thinking-<E>` with `E` one hyphen-component naming an hcn effort word, the stem is `<S>-thinking` with effort `E`; (3) else if the remainder is `<S>-<E>-thinking` with `E` one hyphen-component naming an effort word, the stem is `<S>-thinking` with effort `E`; (4) else if the remainder is `<S>-thinking` and `<S>` does not end with `-<effort-word>`, the stem is the whole remainder and takes no `--effort` (bare thinking-only forms: `claude-4.5-sonnet-thinking`, `claude-4-sonnet-thinking`); (5) else if the remainder is `<S>-<E>` with `E` naming an effort word (`-extra-high` reads as `xhigh`), the stem is `<S>` with effort `E`; (6) else the slug is its own stem: it resolves through its row when one exists (bare medium-tier slugs like `gpt-5.2` are the `medium` value of their row), and is bare-only when none exists. A bare slug maps to `medium` only when its row has no explicit `-medium` entry; if a future `models.txt` lists both a bare slug and an explicit `-medium` slug for one stem, transcription MUST fail rather than double-map `medium`. Every thinking spelling in `models.txt` maps: infixed forms via step 2 (`claude-opus-4-8-thinking-low`), suffixed forms via step 3 (`claude-4.6-sonnet-medium-thinking`, `claude-4.6-opus-high-thinking`, `claude-4.6-opus-max-thinking`, `claude-4.5-opus-high-thinking`), bare forms via step 4. |
| Effort ladder | The set of hcn effort words one family offers. There is no uniform ladder across families. Cursor's `extra-high` spelling normalizes to the hcn word `xhigh` table-side (the `gpt-5.5` row maps `xhigh` to `gpt-5.5-extra-high`); hcn never accepts `extra-high` as an effort word. |
| Trust gate | Cursor refusing an untrusted workspace (exit 1, stderr `Workspace Trust Required ...`) unless `--trust`, `--force`, or `--yolo` is passed. |
| `onMissing: "create"` | Resuming an unknown session id starts a fresh session under that id (exit 0) instead of erroring. Cursor shares this with pi and muse. |
| Refusal | hcn declining before spawn (exit code 2): the call cannot be expressed on cursor. |
| Native error | Cursor failing on its own arguments (exit code 1, class `native`): verbatim stderr, exit code as data. |
| Divergence | A capability cursor cannot express, reported instead of faked. Effort at profile, user-config, or project-config tier always reports divergence on cursor (dropped in `resolve-options.ts`; the harness default runs; the record names the tier and the `effort` key); only arg-tier `--effort` enforces and can refuse. This is the established explicit/divergence split, per the muse memory-gap precedent. |
| Probe | A numbered capture run in the spike (`out/<probe>.{argv,stdout,stderr,exit,secs}`), cited as evidence below. |
| Observed / documented | Observed means a logged-in probe run saw it; documented means Cursor's public docs state it. No claim in this RFC rests on Cursor's shipped code. Where the background research disagrees with the spike report, the spike report wins. |

## Motivation

A consumer that wants a Cursor run today shells out to `agent` directly and re-implements identity parsing, resume flags, failure naming, and question detection that hcn already owns for four harnesses. That duplication is exactly what the normalizer exists to remove. The cost of adding cursor without a written contract is the familiar one: a new `HarnessName` member touches every `Record<HarnessName, ...>` and every exhaustive switch, a new failure class touches precedence and retry policy, and the effort mechanism is genuinely new (no existing harness resolves effort into the model id). Those are design decisions someone could reasonably disagree with, which is the test for writing an RFC rather than a task list.

### Effort mechanism (adapts owner decision 6)

The owner chose "add a render kind" when the evidence suggested bracket params. The spike then showed brackets are REJECTED at runtime (probes 27/28: `Cannot use this model`, exit 1, zero inference consumed) and effort is a slug suffix with per-family ladders (spike Q9/Q10, addendum F). This RFC therefore adapts decision 6 to the observed fact: there is no effort flag on cursor, so effort resolves into the `--model` slug. The adaptation is recorded here; owner answer 1 (2026-09-17, Resolved question 1) confirms the bare-slug-is-medium rows, which ship as specified.

Composition site and order (normative): resolution happens once, at the plan-turn resolve step, on launch and resume alike. After `resolveEffectiveOptions` (launch) or directly on the parsed turn options (resume), when the descriptor's effort spec kind is `effort-in-model` and arg-tier `--effort` is present, the step calls `resolveEffortSlug` and replaces `opts.model` with the resolved slug BEFORE `buildSpawnArgv`. The model the resolver takes is the arg-tier `--model` when present, else the already-resolved `opts.model` when a lower tier supplied it (a config-tier `model` on launch; `model` is not a `DEFAULT_TURN_PROFILE` key, so the profile tier never supplies it), else absent. On resume no profile or config resolution runs by existing design (`plan-turn.ts:293-296`, the launch-only `resolveEffectiveOptions` block), so the parsed `--model` arg is the only model source there. A resolver refusal surfaces like any other argv refusal (exit 2). Capabilities (`stream-turn.ts` reads `opts.model` from `plan.options`) and the decoder therefore see the real slug that ran; provenance does too, because the step rewrites the value of the provenance entry that supplied the model (the arg-tier `model` entry, or the config-tier entry when the model came from config) to the resolved slug, leaving its tier untouched. When no `model` provenance entry exists (the common case: `model` is not a `DEFAULT_TURN_PROFILE` key, and the config loop writes an entry only for keys the config sets, so an arg-tier `--model` with no config `model` leaves no entry), the plan step appends an arg-tier `model` entry holding the resolved slug. On resume, no provenance is produced at all (`plan-turn.ts:293-296`), so provenance stays absent as today. The requested stem is not kept in provenance: every stem-to-slug mapping is pinned in the Phase 4 matrix, and each slug reverse-indexes to exactly one `(stem, effort)` pair. `turnTail` owns the `--model` token and validates the final value with the existing `validateModel`; it performs no family lookup. `turn-options.ts` validates the effort word only. No `EXPRESSIBLE` change is needed: the per-tier awareness lives where tiers exist (the `resolve-options.ts` profile loop) and in the resolver, not in the per-harness expressibility predicate.

Tier rule (normative): only tier `arg` is explicit on cursor. Tiers `profile`, `user-config`, and `project-config` NEVER reach the renderer: the profile loop drops them with a divergence record that names the tier and the `effort` key (effort is a `DEFAULT_TURN_PROFILE` key, so config-file values arrive through that loop's `sourceTier` branch: the skip-and-report path records the unrenderable entry with tier `profile`, `user-config`, or `project-config` as applicable, and `writeProvenance` prints the recorded tier, so the owner can see which file set it) and the harness default runs. This is why a variant slug (which already pins effort) can never conflict with a non-arg default, why bare `hcn run cursor` keeps working, and why a machine-wide `effort` in `~/.config/hcn/config.json` (valid on all four existing ladders, `config.ts:69-72`) does not break cursor. Only an explicit `--effort` flag enforces and can refuse.

Resolution rules (normative), applied in order inside the one resolver; the first applicable rule wins:

- Model checks run before effort checks. A `--model` value that is neither a slug in `vocabulary.models` (plus aliases) nor a key of `effortSlugs` MUST refuse with `unknown-model`, with `supported` following the existing `unknown-model` convention. So `--model claud-opus-4-8-high --effort high` (a typo) refuses as a model problem before any effort rule runs.
- `--model <stem>` with no `--effort`, where `<stem>` is a key of `effortSlugs` but not itself a slug (for example `claude-opus-4-8`, or a thinking stem like `claude-opus-4-8-thinking`), MUST refuse with `unknown-model`, `supported` set to that stem's row slugs (the narrow actionable list, not all 223). A stem is not a selection.
- `--model <stem> --effort <E>` MUST resolve to `effortSlugs[stem][E]`. This rule precedes the variant rule below, so a value that is also a stem key still resolves here: `--model gpt-5.2 --effort high` resolves to `gpt-5.2-high` (likewise `gpt-5.1` and `gpt-5.3-codex`, whose bare slugs are their rows' `medium` values). When the row has no `E`, the call MUST refuse with `unknown-effort`, `supported` set to that stem's ladder (for example `--model kimi-k3 --effort medium`: kimi-k3 offers low/high/max only).
- `--model <variant-slug> --effort <E>` where the slug is a plain or thinking VALUE in any row MUST pass through unchanged when `E` equals the slug's effort (found by reverse-indexing the row; the idempotent case: `--model gpt-5.2-high --effort high` renders `gpt-5.2-high`), and MUST refuse with `invalid-option-value` otherwise. A variant slug already pins effort; a conflicting effort is a caller error, not a second selection.
- `--model <fast-slug> --effort <E>` where stripping one trailing `-fast` reverse-indexes to `(stem, E0)`: when `E` equals `E0` the slug passes through unchanged (the idempotent case: `--model gpt-5.2-high-fast --effort high` renders `gpt-5.2-high-fast`); otherwise the call MUST refuse with `invalid-option-value`. A `-fast` twin pins effort exactly like a plain variant slug: there is no reattach and no switch to a different twin, so a combination with no listed twin can never be emitted. This is an idempotence check, not composition.
- A `-fast` slug whose stripped base is not a row value (for example `composer-2.5-fast`) is opaque: any `--effort` with it refuses `unknown-effort` with empty `supported`.
- Arg-tier `--effort` with no model from any tier MUST refuse with `unknown-effort`: without a family there is nothing to resolve against. On launch this means no arg `--model` and no config-tier `model`; on resume the parsed `--model` arg is the only source, so resume with `--effort` but no `--model` refuses identically.
- Arg-tier `--effort` with a bare-only model (`auto`, `composer-2.5`, and the rest in Terminology), from any tier, MUST refuse with `unknown-effort`, `supported` empty: the stem is a complete selection with no ladder.
- An `--effort` word outside `vocabulary.efforts` MUST refuse with `unknown-effort`, `supported` set to the union ladder. `extra-high` is not an effort word; the `gpt-5.5` row already maps `xhigh` to `gpt-5.5-extra-high`.
- Slug construction by string concatenation is FORBIDDEN: families are irregular (default display tiers vary: `-high` usually, `-xhigh` for `claude-opus-4-7`, `-medium` for `claude-4.6-sonnet`, `-max` for `kimi-k3`; `thinking` is infixed or suffixed per entry), so only table lookup resolves. An `effortSlugs` row MUST contain exactly the slugs `agent models` lists for that stem at `verifiedAgainst`, as derived by the Stem rule.

Rejected alternative: client-side `<base>-<effort>` concatenation. It fails on the first irregular family and would emit slugs Cursor refuses pre-flight, turning a library refusal into a native error.

### Stream decoding

A new `cursor` reader in `interpretation/content.ts`, consumed by the existing `decodeLine`/`decodeParsed` pump. The reader needs per-turn state (pending `call_id`s, query args by `toolCallId`), and content readers are stateless (`content.ts:244-255`), so the state lives in an opaque per-reader value owned by interpretation and threaded by execution without inspection. The contract is return, not mutation: the cursor reader takes `(record, state)` and returns `{ events, state }`, which keeps interpretation side-effect free per AGENTS.md ("pure functions return values"; only `decode.ts` in execution mutates `DecodeState` today, and this RFC keeps it that way). Concretely: `content.ts` owns the state type plus a pure `freshCursorReaderState()` constructor; an interpretation factory builds it per harness (cursor state for cursor, null otherwise); execution holds it in one generically-named `DecodeState` slot. `contentEventsOf(h, raw)` keeps its two-argument array shape for stateless callers (`interpretation/context-inspection.ts:173` and the 19 test call sites in `test/interpretation/content.test.ts` and `test/interpretation/content-rate-limit.test.ts` stay untouched); a new stateful entry point `contentEventsWithState(h, raw, state)` returns `{ events, state }` for every harness (the other four readers ignore the state and pass it through), and `decode.ts:190` is its one production call site, threading the returned state. Execution never reads cursor fields out of the state, so no harness protocol literal enters the execution layer (ADR 0005 and the protocol-ownership gate hold; the purity gate passes unchanged since interpretation gains no `node:` import). The execution-layer change is exactly this threading: the slot, the factory call beside `freshDecodeState`, and the stateful call with the `.events` read. State resets on turn start (constructed wherever `freshDecodeState` is constructed for a turn; reuse across turns is a bug the tests pin). Each map is bounded at 128 entries with drop-oldest eviction, and an evicted `call_id` moves into a bounded tombstone set (same 128 bound, drop-oldest): a `completed` for a tombstoned id emits no second `tool` event (`success` emits nothing further; `rejected` emits the denial error only, since the `tool` event already fired at `started`), so machine consumers double-count no invocation within the 256-entry bound (more than 256 calls in flight in one turn would evict an id from both sets and re-emit its `tool` event; that scale is not a practical turn shape, so the bound is stated, not solved). `decodeIdentity` needs no cursor arm: the init record matches the descriptor-driven `{type: "system", subtype: "init"}` plus `session_id` shape it already owns.

### Autonomy, modes, and trust

- hcn autonomy renders `--force` on cursor (descriptor `autonomy.flag`). `--force` is the full autonomy grant: unattended edits and non-allowlisted shell run with no `interaction_query` lines (probes 16/17). On cursor that grant ALSO bypasses the workspace-trust gate per run without persisting anything (probes 31/32), unlike `--trust`, which persists `.workspace-trusted`. So turning `--autonomy` on weakens the gate for that run, deliberately and visibly: the caller asked for unattended execution and got it. This matches the existing codex precedent, where every run carries `--skip-git-repo-check` in `baseFlags` (`codex.ts`), bypassing codex's trusted-directory check without a per-call decision.
- hcn MUST NOT pass `--trust` itself, and passthrough cannot carry it: tokens after hcn's bare `--` join the positional prompt (probe 40: `-- --trust` in an untrusted workspace exits 1 with the trust stderr; probe 41: `-- --continue` becomes the literal prompt text `pong41 --continue` on a fresh session). A caller that wants `--trust` invokes `agent` outside hcn and owns the persisted state.
- `--mode plan|ask` and `--approve-mcps` have no v1 expression: plan/ask are read-only harness modes with no turn-option key. Passing them has no argv spelling. `--sandbox` has no v1 expression: no spelling confines headless (see Sandbox), so cursor carries no sandbox spec and an explicit `--sandbox` refuses `unsupported-option`, while profile and config-tier sandbox values diverge through the existing no-spec split.
- `--workspace` / `--add-dir` targeting is the spawner's job (spawn `cwd`), as on codex; `--workspace` evidence (probe 30: `init.cwd` is the workspace dir, session filed under its md5) is what makes the resume guard resolve the cwd it actually ran in.

### Sandbox

Owner answer 4 (2026-09-17) takes alternative (b): verify `--sandbox` headless, and add a spec only if it is headless-stable. Revision 07 specified a one-member `danger-full-access` spec from the `--force` matrix (addendum section K). Revision 08 re-probed WITHOUT `--force` (addendum section L, probes 70-71): nothing confines, so the spec leaves and cursor keeps refusing `--sandbox` with `unsupported-option`.

Method (evidence anchor): spellings `--sandbox enabled` and `--sandbox disabled` plus a no-flag baseline, every run WITHOUT `--force` in the trusted workspace `ws-main` under a scratch `CURSOR_CONFIG_DIR` whose allowlist grants the exact probe commands (`Shell(printf)`, `Shell(cat)`, `Shell(curl)` per the documented token grammar), so the approval layer grants each call; cells (a) a shell write outside the workspace, (b) an edit inside the workspace, (c) a network fetch, (d) a read outside the workspace; 3 runs per cell (36 captures, `out/70-*`).

Observed: all 36 captures exit 0 with empty stderr and zero `interaction_query` lines. Inside edits run 9/9 and outside writes land 9/9 (shell `exitCode` 0, file present with content `x`) under both spellings and the baseline. Network returns 200 in 9/9 and outside reads succeed 9/9. Two cell-(a) runs show one `rejected` completion with an empty reason for a variant command the model composed (`printf x > ...; echo $?`), then run the exact allowlisted command to `exitCode` 0 in the same turn: an allowlist-shape miss on the variant, not confinement. The curl trailing-`.` anomaly from section K recurs (6 of 9 runs exit 6 on the echoed `.` host while example.com still returns 200).

Derivation (normative, the fixed rule): inside runs plus outside runs maps a spelling to `danger-full-access`; inside runs plus outside confined would map to `workspace-write`; inside denied plus outside confined to `read-only`; anything else maps nowhere. Inside edits run and outside writes land under every spelling, so no spelling maps to any member. The no-`--force` matrix agrees with the `--force` matrix: no confinement was observed for granted commands (granted by `--force` or by an allowlist entry) on agent `2026.09.15-d2fe57e`. Not tested: a non-allowlisted command without `--force` under `--sandbox enabled`, and an outside write target outside the temp directories. `agent sandbox --help` presents sandbox mode as an alternative to allowlist mode, so granted commands may run outside the sandbox; the result is scoped to granted commands.

Result (normative): cursor carries NO `turnOptions.sandbox` spec, and no `spellings` record exists on the `flag-value` render. An explicit arg-tier `--sandbox` of any value refuses `unsupported-option` with empty `supported` (no spec exists, the same standing as `--access read`); profile and config-tier sandbox values diverge with tier-and-key provenance through the existing no-spec split. A spec that only renders `disabled` for `danger-full-access` would repeat today's default argv and does not justify new vocabulary.

Conflict note: no source documents `--sandbox enabled` plus `--force` as conflicting. `agent --help` describes `--sandbox <mode>` ("Explicitly enable or disable sandbox mode (overrides config)", choices `enabled`/`disabled`) and `--force` ("Force allow commands unless explicitly denied") with no conflict note; `agent sandbox --help` names `enable`, `disable` (allowlist mode, the default), `reset`, and `run`; the public docs sandbox section names only `/sandbox` and `--sandbox <mode>` with an interactive network toggle. The observed non-confinement therefore stands as sandbox behavior, not as a flag conflict.

Re-probe rule: on every `verifiedAgainst` bump, re-run the section-L matrix (at least one run per cell per spelling, without `--force`), plus two cells the section-K and section-L matrices did not cover: a non-allowlisted command without `--force` under `--sandbox enabled` (record whether approval denies it or it runs, and whether it is confined), and an outside write target outside the temp directories (for example a scratch path under `$HOME`); if a spelling confines under the fixed rule (inside runs with outside confined, or inside denied with outside confined), re-add the observed member through the normal spec process. Until then `enabled` stays unrendered and unmapped.

Tests: a unit test pinning explicit `--sandbox` to `unsupported-option` on cursor (launch and resume) plus profile-tier divergence; no argv-corpus sandbox rows and no `spellings` shape test. Fixture capture of the matrix cells stays in the candidate list as evidence.

### Passthrough

ADR 0003 promises that a wrong-harness flag after hcn's bare `--` "fails in the harness itself and surfaces as a native error (exit 1)". On cursor that promise does not hold: the CLI takes a variadic positional prompt and documents no `--` end-of-options handling (probe 50), so every passthrough token joins the prompt as text and the run succeeds with exit 0 (probe 41: prompt `pong41 --continue` on a fresh session). A caller's native flags on cursor would silently rewrite what the model is asked, with no signal. This RFC therefore declares a descriptor-driven exception to ADR 0003, not validated passthrough and not an amendment: `launch.passthrough: "prompt-joins"` states the behavior as data, and any non-empty passthrough tail on such a harness refuses before spawn. ADR 0003's deferral of descriptor-validated passthrough stands; this uses one declared behavior value for one refusal, with no flag list to maintain and no harness-name branch.

The refusal is typed: issue `unsupported-passthrough` (new `RefusalIssue` member with its `buildRefusalMessage` arm), message naming that cursor joins post-`--` tokens into the prompt with the offending tokens as detail, `supported` empty, hint naming the stay-on-harness alternative per ADR 0002 ("remove the tokens after `--`; to pass native flags, invoke `agent` directly"). Consumers are named in member 5 above; plan-turn surfaces it through `buildSpawnArgv` like every other argv refusal, exit 2. There is no `--workspace` plus `--resume` passthrough guard anywhere in this RFC: that combination cannot occur, because hcn has no `--workspace` option and passthrough tokens never become flags.

### Identity and resume

- Identity is minted by Cursor and read from `system/init.session_id` (owner decision 4). No id flag exists at launch; `decodeIdentity` announces on first sight per the existing rules.
- Resume is id-stable: probes 21a/21b/22 show the same `session_id` across resumes with recalled facts, so no rotation handling is needed.
- `onMissing: "create"` activates the two existing guards with no code change beyond the descriptor: the pre-spawn refusal in `cli/run.ts` (and `cli/session.ts:207-225`) when the computed store path is missing, and the pre-spawn warning in `stream-turn.ts`. Both depend on computing the path, which is why `md5-hex` and `rootEnv` are load-bearing, not decorative. A wrong computed path refuses a valid resume with exit 2 (the class of bug fixed in #103), so the precedence table above is normative, not advisory.
- `--resume=-N` indexing and `--continue` resolve most-recent inside the CLI (probes 22/23). Neither is reachable through hcn in v1: hcn has no most-recent option, and `--resume=-1` fails the session-id shape check (see Resume-last).
- Passthrough needs no resume guard: passthrough tokens join the prompt as text (see Passthrough) and never reach Cursor as flags, so a `--workspace` (or `--add-dir`) token after `--` cannot move the session under a different md5. The guard always computes from the spawn cwd, which is where the session files. A real `--workspace` flag would file elsewhere (probe 30), but hcn has no such option: targeting is the spawner's job.
- Malformed ids fail natively before auth (probe 25); hcn's UUID-shape grammar refuses them first with `invalid-option-value`, matching the native behavior.
- A SIGTERM-killed session resumes cleanly with history intact (probe 35); the guard sees the stored session and the resume proceeds.

### Resume-last (moved to its own RFC in draft-06)

Owner decision 2026-09-17: hcn gains a `--resume-last` option. Review draft-05 (findings B1/H2) showed the design needs cross-harness evidence and a safety policy, which is a separate unit of work, so the design moved to its own RFC (to be drafted next, likely number 06). This RFC keeps no resume-last design: no flag, no render, no refusals, no tests. For cursor v1, most-recent resume is not reachable through hcn: `resumeLast: { flag: "--continue" }` stays as descriptor data for `parse-resume.ts` only.

Errata 2026-09-17 (RFC-06 Phase 5, this RFC stays Accepted): the "not reachable through hcn" sentence above is SUPERSEDED. RFC-06 (Accepted) flips cursor `resumeLast.headless` to `true` now that this RFC has landed (merge to main), so `hcn run cursor --resume-last` renders `agent -p --continue <prompt>` with the stream flags, model, and `--force` per `turnTail`. The `parse-resume.ts` role is unchanged.

The next RFC starts from these B1/H2 facts:

- Codex `--last` is valid only in `exec resume` (`codex.ts:98-99`); rendering it into launch argv produces invalid codex argv, and resume argv takes different turn-option renders (sandbox uses `resumeRender` `-c sandbox_mode`).
- Headless `muse exec` has no `--last` (`muse resume --last` is the interactive subcommand, `muse.ts:87-88`); the muse `resumeLast` flag is parse data, not a render target.
- Claude and pi DO have most-recent resume (`claude --continue`/`-c`, `pi --continue`/`-c`), although their descriptors carry `resumeLast: null`: a descriptor gap, not a harness fact.
- No guard or warning fires without an id (the `stream-turn.ts:249` create-on-missing warning and the `run.ts`/`session.ts` store checks all key off a resume id), cursor resume creates on missing, and the `resume-last.ts` "stranger" stance (most-recent over a race window can resume another run's session) still stands and needs a policy: warn, refuse, or accept-and-document, plus a signal that tells resumed from fresh.

### Version and update plumbing

- `versionSource: { kind: "installed" }` routes `check-versions` to the local `agent --version` fallback, skipped where the binary is absent; weekly CI npm polling does not cover cursor.
- `verifiedAgainst` bumps only with a full re-verification (`smoke:seven`, `smoke:questions`), fixture re-capture, and `escalation.observedOn` transcription, per the AGENTS.md convention. The `models.txt` transcription is part of every bump: the list is date-sensitive.
- Auto-update has no off switch, so a version can move under a pinned descriptor between runs. This is a known drift risk (owner decision 8): `verifiedAgainst` never rejects a working invocation, and native failures stay authoritative.

## State Machine

```text

INIT --> REASONING (on: thinking/delta; no hcn event)
REASONING --> REASONING (on: thinking/completed, assistant delta; token events)
REASONING --> TOOL_CALL (on: tool_call/started; emits one tool event,
  records call_id as pending)
REASONING --> QUERY (on: interaction_query pair for an unknown call_id;
  no event; records query args by toolCallId; ask-question call in
  default mode, probe 20)
QUERY --> TOOL_CALL (on: tool_call/started with the matching call_id;
  emits one tool event)
TOOL_CALL --> TOOL_CALL (on: interaction_query pair mid-call; no event;
  the approval flow, probe 15)
TOOL_CALL --> REASONING (on: tool_call/completed success; no event)
TOOL_CALL --> REASONING (on: tool_call/completed rejected; emits non-terminal
  error with the denial field; turn continues, exit stays 0)
REASONING --> TOOL_CALL (on: tool_call/completed with unknown call_id
  and success; emits the tool event only, no denial)
REASONING --> TOOL_CALL (on: tool_call/completed with unknown call_id
  and rejected; emits the tool event first, then the denial error;
  a denial can land with no preceding started, probe 15 lines 39-41)
TOOL_CALL --> TOOL_CALL (on: tool_call/completed with tombstoned call_id;
  emits nothing on success, denial error only on rejection; no second
  tool event ever)
REASONING --> RESULT (on: result/success; turn end)
REASONING --> RESULT (on: result with other subtype or is_error;
  terminal error, task failure path)
SPAWN --> TRUST_REFUSED (on: exit 1 with trust stderr; no stream at all)
SPAWN --> NATIVE_ERROR (on: exit 1 with model/resume stderr; empty stdout)
ANY --> KILLED (on: SIGTERM/SIGINT to the process; stream truncates with
  no result line, exits 143/130; the stored session stays resumable, probe 35)
RESULT --> CLEAN (on: exit 0)
```

Timeout behavior: the existing stall clock and wall-clock deadline apply unchanged; stdin is closed at spawn so the notes-07 hang (open stdin blocks exit after `result`) cannot occur. Invalid transitions: any line that is not JSON on a `stream-json` stream is wall-scanned (limit/auth) and otherwise ignored, per the existing pump; a `tool_call/completed` with neither `success` nor `rejected` result is ignored like any unknown shape.

## Error Handling

### Failure classification

Failures are named after spawn; refusals before spawn are exit 2 and ride the existing issues plus the new `unsupported-passthrough` issue specified in Passthrough. Cursor writes no JSON on stdout for any failure mode: every failure has empty stdout and plain-text stderr (spike Q14).

### Escalation

Denied calls never escalate (no ACP channel exists to answer through). The model's final text after denials is ordinary prose: the standard question detection applies to it unchanged. If it carries an `hcn-question` block, the turn ends `awaiting-input` like any other harness; if not, the turn is `clean` with informational `error` events attached.

## Security Considerations

**Trust boundaries are unchanged.** hcn trusts its descriptors and config tiers, treats harness stdout as the least trusted input (the session id is shape-checked before it becomes a path segment; replacements in `storePath` stay literal), and writes its escalation preamble into the model's context exactly as for other harnesses. This RFC adds no new input: the md5 slug and env-root resolution consume cwd and env the CLI already reads.

**The trust gate MUST NOT be weakened silently by hcn.** hcn never passes `--trust` (it would persist `.workspace-trusted` beyond the process) and never sets `CURSOR_CONFIG_DIR` or `XDG_CONFIG_HOME` for the child. Autonomy renders `--force`, which is the full unattended grant (edits plus non-allowlisted shell, probes 16/17) and bypasses the gate per run without persisting anything (probes 31/32). With `--autonomy` on, the gate is therefore bypassed for that run: a deliberate, visible caller choice, not a silent weakening. There is no passthrough channel for `--trust` (probes 40/41), so a caller that wants it invokes `agent` outside hcn and owns the persisted state.

**Input validation moves with its rule and MUST NOT weaken.** The session-id UUID check, the `CLEAN_SELECTOR` model grammar, the matcher bounds (pattern length, count, flags), and the `md5-hex` slug computation each keep one owner. `detectTrustRefusal` compiles under the same bounds as every other matcher, so a crafted override file cannot widen it into a backtracking hazard.

**Permissions model.** Cursor's allow/deny lists live in config files hcn never writes. The v1 tools surface (`no-lists`, null flags) means hcn can neither grant nor deny Cursor tools per call; `--tools` refuses instead of pretending. The access preset has no cursor arm, so access values refuse rather than silently running wide.

**Prompt injection surface.** The escalation preamble is not edited and no new model-facing text is added. Denied-call reasons (including empty strings) are data in non-terminal error events, never instructions.

**Blast radius.** The worst case is a wrong argv, a wrong store path (refusing a valid resume or warning on a fresh one), or a misclassified failure on one process hcn spawned. hcn holds no credentials and writes no store; Cursor authenticates under the user's own session. The `store.rootEnv` resolution only READS `CURSOR_CONFIG_DIR` / `XDG_CONFIG_HOME` to locate the store; it never exports them to the child beyond what the user's environment already carries.

**Data sensitivity.** Fixtures MUST carry no account material: `agent status` / `agent about` captures (account email), `cli-config.json` (email plus auth-adjacent metadata), and any token-shaped string are banned from fixtures. Stream fixtures keep run-specific UUIDs and absolute scratch paths only after path normalization; the spike's secret scan over `out/` was clean and the implementation MUST re-scan before capture. `apiKeySource` is the string `login`, never a key.

## Alternatives Considered

1. **Bracket params for effort** (`model[effort=high]`). Considered because the `--help` text shows the syntax. Rejected: probes 27/28 prove the runtime refuses brackets pre-flight on this version, and the parameters page documents no bracket syntax. Only slug suffixes work.
2. **Hidden `--new-session-id` for caller-assigned identity.** Considered because the research confirmed the flag validates UUIDv4. Rejected: it is undocumented, and owner decision 4 forbids depending on hidden flags. Identity stays harness-minted.
3. **ACP for persistent sessions and native approvals.** Considered because it is the only channel Cursor offers for answering approvals and questions. Rejected for v1: hcn has no ACP client, one ACP client is a separate feature, and owner decision 3 scopes v1 to one-shot turns plus resume.
4. **Passing `--trust` by default.** Considered because it would make untrusted workspaces just work. Rejected: it persists trust beyond the process, and owner decision 7 forbids it. The decision stands on its own. (Codex shows the other shape of this trade: hcn passes `--skip-git-repo-check` on every codex run, bypassing that gate centrally. Cursor differs because `--trust` persists `.workspace-trusted` beyond the process; the per-run bypass hcn does pass (`--force` via `--autonomy`) persists nothing, so the bypass rides the per-run autonomy grant instead.) There is no passthrough channel either (probes 40/41), so callers that want `--trust` invoke `agent` outside hcn.
5. **Mapping the trust refusal onto class `native`.** Considered because the existing post-queue path would classify it without a vocabulary change. Rejected: `native` names the harness's judgment on its arguments, while trust names a caller-fixable gate; conflating them sends the human to read verbatim stderr instead of an actionable remedy. The owner chose a typed class.
6. **Reusing `dash-separators` for either cursor slug.** Considered for the projects-side slug. Rejected: it replaces only `/` and `.` with no collapsing or trimming, which does not match the observed rule, and v1 needs no projects-side member at all.
7. **Client-side `<base>-<effort>` slug concatenation.** Considered as a smaller change than a family table. Rejected: families are irregular (infix `thinking`, default-tier `-high`, partial `-fast` coverage), so concatenation emits slugs Cursor refuses. Enumeration is the only honest mechanism.
