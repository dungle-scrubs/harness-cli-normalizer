Criterion 4 detail. `stdinPolicyOf(h)` returns the descriptor field verbatim
(`dimensions.ts:9`). `stream-turn.ts:235` maps `"close-required"` to the
spawn option `"close"` and everything else to `"inherit"`.
`node-deps.ts:114` maps the spawn option `"close"` to Node's stdio
`"ignore"`, `"pipe"` to `"pipe"`, and anything else to `"inherit"`. So pi and
codex get fd 0 on `/dev/null`, which is what criterion 4 calls `ignore`. The
stated reasons: pi reads stdin even in `-p` mode and a backgrounded call
without a redirect hangs (`pi.ts:4-5`); `codex exec` appends piped stdin as a
`<stdin>` block and can block on an open stdin, verified against 0.147.0
(`codex.ts:87-89`). claude and muse carry no reason at their `stdin` line -
`inherit` is the descriptor default and claude needs the parent tty for its
statusline channel. Session mode overrides all four to `pipe`
(`session-hardening.test.ts:40`).

### F-D6-6 `src/execution/stream-turn.ts:496`

- question: Q1
- severity: major
- coverage: `no_recorded_issue`
- failing scenario: a missing harness binary is classified `native` with
  `retryable: false`. `failure.ts:52` excludes `native` from `retryableOf`.
  The choose-model contract treats a missing CLI as a reason to walk the
  ordered `fallbacks`, and it reads `FailureSummary.retryable` to decide. A
  delegating agent that routes to `glm-5.2` on a machine without `pi`
  installed receives `class: "native", retryable: false` and stops instead of
  falling back. The same condition taken through the sync-throw branch
  (`stream-turn.ts:242`) yields `class: "transport", retryable: true` - two
  classes for one condition, decided by whether the runtime reports ENOENT
  synchronously or asynchronously. The real adapter always reports it
  asynchronously, so the `transport` branch is unreachable in production.
- evidence: `SCRATCH/audit/live/d6-enoent.mjs` run against the built `dist/`.
  Node 26.4.0 and Bun 1.3.10 both produce
  `failure {class:"native", retryable:false, nativeExitCode:127}` and
  `done {exitCode:null, cause:"crash"}`. The unit test that claims to cover
  this, `runner-hardening.test.ts:274-298`, injects
  `spawn: () => { throw new Error("ENOENT: claude not found") }` and asserts
  `class: "transport", retryable: true` with `done.exitCode: 127,
  cause: "failed"`. It exercises a branch the adapter never takes. The event
  order differs too: the sync branch emits `error` then `failure`, the real
  branch emits `failure` then `error`.
- smallest change that flips it to pass: in `streamTurn`, detect the
  adapter's spawn-error tail (or have `node-deps.ts` surface a spawn-failure
  flag on `SpawnedProcess`) and route it to `failureFromTransport` the way

  on both branches.

### F-D6-8 `src/knowledge/muse.ts:78`

- question: Q1
- severity: note
- coverage: `no_recorded_issue`
- failing scenario: muse carries `stdin: "inherit"` and, per H7,
  `verifiedAgainst` 0.1.0 against 0.2.1 installed. With `inherit`, the child
  receives the parent's fd 0 verbatim (`node-deps.ts:114`). When the parent's
  fd 0 is `/dev/null` or a closed pipe, a read returns EOF and nothing
  blocks. When the parent's fd 0 is a controlling terminal and the parent is
  backgrounded, a child read raises SIGTTIN and stops the process group -
  the observable symptom is the same wedge the pi rule exists to prevent.
  Whether `muse exec` 0.2.1 reads fd 0 at all is not established by the
  descriptor.
- evidence: `src/knowledge/muse.ts:78` with no accompanying reason, against
  `src/knowledge/pi.ts:4-5` and `src/knowledge/codex.ts:87-89`, which both
  state theirs. The charter forbids a live backgrounded muse run in D6, so
  this is reasoned from `node-deps.ts:114` and not observed.
- smallest change that flips it to pass: re-verify `muse exec` stdin
  behavior against 0.2.1 and record the reason at `src/knowledge/muse.ts:78`,
  bumping `verifiedAgainst` and `versionSource` together.
