## Findings

### F-D11-1 `src/cli/run.ts:35-38`

- question: Q1
- severity: blocker
- coverage: `no_recorded_issue`
- failing scenario: a wrapper agent runs
  `hcn run <h> --json --prompt-file p.txt ...` in the background, captures
  stdout, and branches on the NDJSON. When hcn refuses the invocation
  (unknown flag, unsupported option for the harness, bad `--env`, bad
  `--max-steps`, unknown skill name, leading-dash positional, config error,
  floor violation) the process writes prose to stderr, sets exit 2, and
  writes **zero bytes to stdout**. The agent's stdout reader sees an empty
  stream with no `failure` event and no `done` event, so it cannot tell a
  refusal from a crash without parsing the stderr prose the hcn skill tells
  it never to parse.
- evidence: `audit/live/refusal-probes.txt` probe A
  (`run codex --provider zai/glm-5.2 --prompt hi --json` -> exit 2, stdout
  empty) and `audit/live/nospawn-probes.txt` P3, P6, P7, P8, P9 (five more
  refusal shapes, all exit 2, all stdout empty). In source: `wantJson` is
  read once at `run.ts:111` and is never consulted by any of the eleven
  refusal branches (`run.ts:35-38, 89-93, 101-103, 106-108, 126-135,
  151-160, 171-179, 202-205, 233-236, 246-249, 357-366`). The only stdout
  failure synthesis is the transport catch at `run.ts:489-501`.
  `~/.agents/skills/hcn/SKILL.md:29-31` promises "**2** hcn refused the
  invocation itself (structured - never parse prose; the hint and support
  list are fields)"; the fields exist on `ArgvRefusalError` but never reach
  stdout.
- smallest change: in `src/cli/run.ts`, replace the repeated
  `process.stderr.write(...); process.exitCode = 2` blocks with one helper
  that also calls `writeEventNdjson(failureFromRejected(err))` plus a
  `{kind:"done", cause:"failed"}` line when `wantJson` is true.
  `failureFromRejected` already exists at `src/execution/failure.ts:161`.

### F-D11-2 `src/cli/help.ts:19-88`

- question: Q1
- severity: minor
- coverage: `no_recorded_issue`

  `hcn run --help` to find the skills flag. `RUN_HELP` documents only

  `check-claims.sh` lines 51-71 never list `--skills` or `--session-id`, so

- smallest change: add `--skills <a,b>` and `--session-id <uuid>` rows to

  --help"` list in `check-claims.sh`.

### F-D11-3 `src/cli/exit-codes.ts:7`

- question: Q1
- severity: note
- coverage: `no_recorded_issue`
- failing scenario: `exitCodeForCause` is exported and asserted by
  `test/cli/cli.test.ts:489-494` and `test/cli/question.test.ts:73-75`, but
  no file under `src/` imports it. `src/cli/run.ts:462-467` re-implements
  the mapping inline. The exit-code contract is therefore proven against a
  helper the CLI does not call: a change to `run.ts:462-467` alone would
  leave both tests green. Separately, `streamTurn` yields a
  `class: "rejected"` failure with `cause: "failed"`
  (`stream-turn.ts:162-163, 213-214`) instead of throwing, and
  `run.ts:462-467` has no arm for `failure.class`, so that shape would exit
  1 rather than 2.
- evidence: `grep -rn "exitCodeForCause" src/ test/ scripts/` returns only
  the definition and the two test files. The `rejected` path is unreachable
  from `hcn run` today because `run.ts:327-369` pre-builds argv and catches
  `ArgvRefusalError` at exit 2 first, `parseEnvEntries`
  (`args.ts:59-66`) rejects bad env keys before `stream-turn.ts:139-167`
  can, and `streamingGranularityOf` (`argv.ts:253-263`) never throws. A
  library consumer of `streamTurn` gets exit-code semantics the CLI never
  exercises.
- smallest change: make `src/cli/run.ts` call `exitCodeForCause` at line
  463 and give it a `failure.class === "rejected" -> EXIT_REFUSAL` arm, so
  the tested helper and the shipped mapping are the same code.

### F-D11-4 `src/cli/args.ts:270-321`

- question: Q1
- severity: note
- coverage: `no_recorded_issue`
- failing scenario: `KNOWN_FLAGS` omits `--skills` and `--timeout`;
  `FLAGS_WITH_VALUE` omits `--skills`. `detectPositionalPromptInjection`
  (`args.ts:323-358`) walks argv and skips the value only after a
  `FLAGS_WITH_VALUE` token. A `--skills` value that begins with a single
  dash is therefore read as a positional prompt and refused with
  "positional prompt may not start with '-'", naming the wrong flag. The
  two sets have drifted from the `parseCommonFlags` option table they
  mirror and nothing keeps them in sync.
- evidence: `args.ts:270-304` (`KNOWN_FLAGS`, 33 entries, no `--skills`, no
  `--timeout`) against `args.ts:417-451` (`parseCommonFlags` options, 33
  entries including both). The refusal text is the one seen in
  `audit/live/nospawn-probes.txt` P8.
- smallest change: derive `KNOWN_FLAGS` and `FLAGS_WITH_VALUE` in
  `src/cli/args.ts` from the `parseCommonFlags` option table (string-typed
  entries become `FLAGS_WITH_VALUE`) instead of hand-listing them.

### F-D11-6 `src/knowledge/pi.ts:82`

- question: Q1
- severity: note
- coverage: `no_recorded_issue`
- failing scenario: `hcn inspect pi --argv --prompt hi --model not-a-model`
  renders `["pi","-p",...,"--model","not-a-model",...]` and exits 0. pi's
  vocabulary is `extensible: true` by ratified decision D-008, so a typo in
  a pi model id is not caught by hcn and surfaces only as a native pi
  error at run time. An agent that trusts hcn to validate `--model` before
  spending a turn does not get that on pi.
- evidence: `audit/live/refusal-probes.txt` probe B (stdout
  `["pi","-p","--mode","json","--thinking","high","[prompt:2ch]","--model","not-a-model",...]`,

  `descriptor.ts:324-327` documents the accept rule. claude, codex and muse
  are `extensible: false` (`claude-code.ts:110`, `codex.ts:75`,
  `muse.ts:66`), so only pi behaves this way.
- smallest change: none to the code - the behaviour matches D-008. State it
  in `~/.agents/skills/hcn/SKILL.md` so a caller knows pi model ids are
  unvalidated.

### F-D11-7 `src/execution/node-deps.ts:114`

- question: Q1
- severity: note (unproven)
- coverage: `no_recorded_issue`
- failing scenario: `stdio[0]` is `"ignore"` only when the descriptor says
  `stdin: "close-required"`. pi (`pi.ts:94`) and codex (`codex.ts:90`) say
  that; claude (`claude-code.ts:126`) and muse (`muse.ts:78`) say
  `"inherit"`. A Claude Code wrapper agent that backgrounds
  `hcn run claude` from Bash hands the child whatever fd 0 the wrapper
  shell has. If that fd is a closed pipe rather than `/dev/null`, the
  child's stdin is a descriptor that is not a readable empty stream. No
  evidence either way was produced.
- evidence: `node-deps.ts:110-118` stdio table;
  `stream-turn.ts:235` (`stdinPolicyOf(h) === "close-required" ? "close" :
  "inherit"`); the four descriptor lines above. The permitted pi background
  probe passed (`audit/live/pi-bg.ndjson`), which proves the
  `close-required` arm, not the `inherit` arm. The charter forbids adding
  live runs for this.
- smallest change: none proposed on this evidence. To settle it, run one
  backgrounded `hcn run claude --json` with fd 0 closed (`0<&-`) and check
  for a `done` event.
