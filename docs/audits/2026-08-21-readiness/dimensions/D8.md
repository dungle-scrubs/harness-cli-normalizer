## The round trip in code

One-shot (`hcn run`, the Q1 and Q2 path):

1. `run.ts:292-307` resolves `escalateQuestions` (arg > project > user >
   default true) and writes the provenance line at 384-386.
2. `run.ts:311` composes the preamble onto the prompt. The same composition
   runs on resume turns - the branch at 328-337 rebuilds argv from the
   composed prompt, so an answer turn carries the protocol again.
3. `streamTurn` re-composes idempotently (`stream-turn.ts:128-132`;
   `question.ts:61` short-circuits on the marker).
4. Every assistant `message` event overwrites `lastAssistantText`
   (`stream-turn.ts:367-369`), armed only in true mode.
5. After `proc.exited` and both pumps settle, `emitQuestionIfAsked`
   (`stream-turn.ts:391-414`) runs `detectQuestionBlock` on that text, emits
   the typed `question` event, and sets `asked`.
6. `stream-turn.ts:520-523` turns exit 0 + `asked` into
   `done cause=awaiting-input`; `run.ts:463` maps that cause to process exit 0.
7. The caller resumes: `hcn run <h> --resume <id> --prompt "<answer>"`. The
   id comes from the `identity` event (rendered at `render.ts:19`, or read
   from NDJSON).

Session (`hcn session`, issue #44): `open-session.ts:168` composes the
session-mode preamble on every send; `emitQuestionIfAsked`
(`open-session.ts:194-218`) runs at the turn boundary inside `endTurn`
(225), the cause flips at 226, and the answer is the next `send`
(`session.ts:211-213`) on the same process.

## Timeout - what happens when no answer comes

One-shot: nothing is armed, because nothing is alive. The `question` event
is emitted only after `proc.exited` resolves (`stream-turn.ts:473-475`), the
turn ends `awaiting-input` (520-523), and `hcn` exits 0 (`run.ts:463`). The
harness process is already gone; the answer arrives as a new process
(`--resume`). The only turn timers are the optional wall-clock budget
(`--timeout`, `run.ts:394-402` -> `turnTimeoutMs`, armed at
`stream-turn.ts:318-334`) and the inactivity watchdog (`deps.stallMs`,
`stream-turn.ts:295-317`); both bound the turn, neither bounds the wait for
an answer. A consumer that never answers loses nothing but the session
context, which stays on disk for a later `--resume`.

Session: no timer is armed while waiting either. The three timers in
`open-session.ts` all arm on other events - `KILL_GRACE_MS` inside
`escalate()` (160), `PIPE_GRACE_MS` only after `proc.exited` (473),
`CLOSE_GRACE_MS` only inside `close()` (494). `deps.stallMs` is not read
anywhere in `open-session.ts` (grep: no hit), and `session.ts:97` builds
`nodeRunnerDeps()` with no `turnTimeoutMs`. The child harness stays alive
and idle while `session.ts:200-210` parks on the next stdin line. Whatever
idle timeout the harness itself applies is not hcn's contract and is not
stated anywhere.

## Findings

### F-D8-1 `README.md:134-157` (also `~/.agents/skills/hcn/SKILL.md:78-121`)

- question: Q1+Q2
- severity: major
- coverage: `README.md` no_recorded_issue
- failing scenario: lucid-v2 escalates a `question` to a human and the human
  walks away for six hours. Nothing in README, `hcn run --help`
  (`help.ts:45-50`), or the hcn skill tells the consumer whether hcn holds
  any state, whether a budget expires, or whether the session id stays
  resumable. The code answer is "no timer at all, in either mode" (see the
  section above), but a consumer has to read `stream-turn.ts` and
  `open-session.ts` to learn it, and a wrapper agent (Q1) cannot know
  whether it must bound the wait itself.
- evidence: `grep -i "never answer|no timer|answer.*timeout|idle|indefinit"`
  over `README.md`, `~/.agents/skills/hcn/SKILL.md`, and
  `~/.agents/skills/hcn/references/reference.md` returns nothing. The
  README section 134-157 documents the protocol, the flags, and the resume
  path, and stops there.
- smallest change that flips it: add two sentences to the "Question
  escalation" section of `README.md` (and mirror in `SKILL.md` step 2): a
  turn that ends `awaiting-input` arms no answer timer - the process has
  exited and the id stays resumable; in `hcn session` the process stays
  alive with no idle budget of hcn's own.

### F-D8-2 `src/execution/stream-turn.ts:395-398` (and `open-session.ts:198-201`, 226)

- question: Q1+Q2
- severity: minor
- coverage: no_recorded_issue (both files)
- failing scenario: a worker tries to ask but botches the JSON, e.g.
  ```` ```hcn-question\n{"question":"q","options":[]}\n``` ````. Detection
  returns `{malformed}`, `emitQuestionIfAsked` pushes an `error` event and
  returns before setting `asked`, so `stream-turn.ts:520-523` keeps
  `cause: "clean"` with exit 0. A consumer branching on `done.cause` (the
  documented signal - README:151) reads a completed turn, drops the worker,
  and never escalates, while the worker believes it ended its turn blocked
  on an answer. `open-session.ts:226` has the same shape: `turnAsked` stays
  false, cause stays `clean`.
- evidence: `test/execution/question.test.ts:110-122` asserts exactly this
  outcome - error event present, `done` is `{exitCode: 0, cause: "clean"}`.
- smallest change that flips it: in `emitQuestionIfAsked` (both files), set a
  distinct flag on the malformed branch and let the done cause carry it (a
  `failed` cause, or a new cause the consumer can branch on), instead of
  leaving the turn indistinguishable from a clean completion.

### F-D8-3 `src/cli/run.ts:311` (answer path)

- question: Q1
- severity: minor
- coverage: no_recorded_issue
- failing scenario: nothing validates the resume prompt against the
  question's `options`. `run.ts` never reads `options` (grep: only
  `resolveEffectiveOptions` and turn options), and `session.ts:202-209`
  accepts any non-empty line as a custom answer by design. An out-of-options
  or evasive answer simply becomes the next prompt, and because
  `run.ts:311` composes the escalation preamble onto every turn including
  resumes, the worker may ask again - another `question` event,
  `awaiting-input`, exit 0. Each `hcn run` is a fresh process, so no ask
  counter exists anywhere; an unattended Q1 wrapper that answers
  mechanically can loop ask -> answer -> ask without bound.
- evidence: `grep -n "options" src/cli/run.ts` (no question-options use);
  `test/execution/question.test.ts:149-166` shows the resume turn is
  composed with the same preamble; `scripts/e2e-questions.ts:267` treats a
  second ask as a scenario failure, which is the scenario's rule, not the
  code's.
- smallest change that flips it: state in `SKILL.md` step 3 that the
  answer is unvalidated and a resumed turn may ask again, and have the
  wrapper cap ask cycles - or add an `--answer-to <id>` style path in
  `run.ts` that carries the prior question so hcn can count.
