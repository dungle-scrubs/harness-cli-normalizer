## Findings

### F-D5-1 `src/knowledge/matchers.ts:23`

- question: Q1+Q2
- severity: blocker
- coverage: `no_recorded_issue`
- failing scenario: the shared rate-limit matcher is the bare string `429`
  with no word boundary and no HTTP context. Any harness stderr line
  containing those three digits anywhere - a UUID segment, a byte count, a
  port, an elapsed-ms figure, a line number - classifies the turn as
  `rate-limit`. Because `state.limitSeen` is then true, the guard
  `!state.limitSeen` at `stream-turn.ts:491` suppresses the native and
  transport classification at exit, so a real harness error on the same turn
  is replaced by a fabricated retryable wall.
- evidence: `SCRATCH/audit/d5/fp.ts` - `detectLimitInLine(claudeCode, ...)`
  returns `rate-limit` for `"task_id d3665fd8-fd23-4297-ab53-4528fc517db3"`,
  `"read 4291 bytes from cache"`, `"warn: node:tls deprecation at line
  429"`, `"listening on 127.0.0.1:4290"`, `"elapsed 1429ms"`. Identical for
  `piCli` and `codexCli` (shared matchers). `SCRATCH/audit/d5/wall.ts` drives
  `streamTurn` twice with the same real error: with the UUID line first,
  `done` is `{cause: "limit", exitCode: 2, failure: "rate-limit", retryable:
  true}`; without it, `done` is `{cause: "crash", exitCode: null, failure:
  "native", retryable: false}`. Collision rate on real harness output:
  `test/fixtures/harnesses/muse-readtool.ndjson` has 9 lines containing
  `429` out of 49 (lines 31-37, 41, 42), all inside ids.
- smallest change that flips it to pass: in `SHARED_LIMIT_MATCHERS`
  (`src/knowledge/matchers.ts:23`) replace the bare `429` with an
  HTTP-anchored pattern, for example `\b(?:status|code|http)[^0-9]{0,8}429\b`
  or `\b429\b(?=[^0-9]*(?:too many|rate|retry))`, so a digit run inside an
  identifier cannot match.
