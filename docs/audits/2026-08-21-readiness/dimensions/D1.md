## Findings

### F-D1-1 `src/execution/stream-turn.ts:362`

- question: Q1+Q2
- severity: major
- coverage: `no_recorded_issue`
- failing scenario: `hcn run <h> --json` without `--model` passes
  `opts.model ?? ""` into `decodeLine`, so `capabilitiesOf` calls
  `resolveModel(h, "")`, finds `""` outside `vocabulary.models`, and takes
  the degrade branch at `capabilities.ts:34-41`. Every default run therefore
  announces `identity.capabilities = {vision:false, images:false,
  streaming:"none", session:false, source:"unknown", confidence:"none"}`
  while the turn goes on to emit `token` events on claude, pi and muse and
  `message` events on codex. A consumer that reads
  `identity.capabilities.streaming` to size its reducer - the exact use the
  charter names - is told "none" on every default turn on all four
  harnesses, and is told `session:false` for claude, which has a
  `sessionMode`. The same degrade fires for any pi model other than
  `zai/glm-5.2`, the only curated pi model.
- evidence: `SCRATCH/audit/live/claude.timed`, `codex.timed`, `pi.timed`,
  `muse.timed`, `SCRATCH/audit/live/kill-1.ndjson` and `kill-2.ndjson` -
  six identity events, all six `"streaming":"none","source":"unknown"`.
  The correct answers sit in the descriptors:
  `capabilities.streamingByMode["headless-turn"]` is `token` for claude
  (`claude-code.ts:134`), `message` for codex (`codex.ts:98`), `token` for
  pi (`pi.ts:102`) and muse (`muse.ts:88`) - each matching what arrived.
- smallest change: in `stream-turn.ts` resolve the effective model before
  the decode loop (descriptor default when `opts.model` is undefined) and
  pass that to `decodeLine`, or have `capabilitiesOf` treat an empty
  selector as the harness default rather than an unknown model; better
  still, take `streaming` from `streamingGranularityOf(h, argv)`
  (`argv.ts:253`), which already computes it from the argv actually spawned.

### F-D1-2 `src/execution/stream-turn.ts:514-526`

- question: Q1+Q2
- severity: major
- coverage: `no_recorded_issue`
- failing scenario: a caller sends SIGTERM to `hcn` to interrupt a turn.
  `run.ts:431` relays SIGTERM to the child; claude handles it and exits
  143. `node-deps.ts:144` (`child.on("exit", (code) => resolve(code))`)
  drops node's `signal` argument, and `streamTurn` has no input saying the
  exit was caller-requested, so the classifier at `stream-turn.ts:514-526`
  reaches `exitCode !== 0` and reports `cause:"crash"` with
  `failure {class:"transport", retryable:true}`. The `killed` cause exists
  and is never reached on this path. README's canonical consumer check
  (`README.md:196-199`) then routes a user-initiated interrupt into
  `descendFallbackChain(done.failure)` - a deliberate stop is read as a
  provider outage and re-dispatched.
- evidence: `SCRATCH/audit/live/kill-1.ndjson`, last two lines:
  `{"kind":"failure","class":"transport","retryable":true,"message":"Transport failure (nonzero exit 143) - retry or route to another provider"}`
  then
  `{"kind":"done","exitCode":143,"cause":"crash","failure":{...transport...}}`.
- smallest change: record the caller-requested stop in `streamTurn` - set a
  flag when `deps.signal` is invoked from the CLI's `onSig`, or thread an
  abort signal into `streamTurn` - and classify that exit as
  `cause:"killed"` with no `transport` failure attached.

### F-D1-3 `src/cli/run.ts:432-441`

- question: Q1+Q2
- severity: minor
- coverage: `no_recorded_issue`
- failing scenario: `onSig` sends SIGTERM to the child and then awaits a
  plain `setTimeout(..., KILL_GRACE_MS)` that is never cancelled when the
  child exits early. The timer keeps node's event loop alive, so `hcn`
  cannot exit sooner than 5 s after SIGTERM no matter how fast the harness
  dies. A consumer killing a turn per user interrupt sees a fixed 5 s stall
  on every interrupt, and must add its own SIGKILL timer to shorten it.
- evidence: `SCRATCH/audit/d1-kill.sh` output -
  `kill_at=1787285846.148893`, `wait_returned_at=1787285851.159518`,
  `kill_to_exit_seconds=5.011`, while the child's own exit code (143)
  proves it died of SIGTERM rather than of the grace-expiry SIGKILL.
- smallest change: in `run.ts` `onSig`, keep the escalation timer handle and
  clear it once the `for await` loop over `streamTurn` completes, or
  `unref()` it so it cannot hold the process open.

### F-D1-7 `src/execution/decode.ts:65`

- question: Q2
- severity: minor
- coverage: `no_recorded_issue`
- failing scenario: the identity event's `authority` is copied straight
  from the descriptor constant (`h.identity.authority`), so it describes
  what the harness *accepts*, not what happened to this id.
  `buildLaunchArgv` (`argv.ts:136-144`) never renders `launch.idFlag` -
  the only use of an `idFlag` in the codebase is `buildSessionArgv`
  (`argv.ts:184`) - so a `hcn run` launch never assigns an id and every
  first-turn id is minted by the harness, yet claude, pi and muse all
  report `"authority":"caller-assigned"`. A consumer branching on
  `authority` to decide whether it already knows the id is told the wrong
  thing on every launch. It also makes the charter's post-kill check
  (`pgrep -fl claude` for a child carrying the session id) vacuous: the id
  is never in the child's argv.
- evidence: `SCRATCH/audit/live/kill-1.stderr` spawn line
  `claude -p --effort high [prompt:984ch] --output-format stream-json
  --verbose --include-partial-messages` - no `--session-id` - while
  `kill-1.ndjson` announces
  `{"kind":"identity","sessionId":"aa0b85d6-...","authority":"caller-assigned",...}`.
  `pgrep -fl aa0b85d6-...` returned nothing both before and after the kill.
- smallest change: in `src/execution/decode.ts`, set the event's
  `authority` from whether this turn supplied the id (`state.requestedId
  !== null`) rather than from `h.identity.authority`, or rename the
  descriptor field to say it is a capability.

### F-D1-8 `src/cli/run.ts:257-280`

- question: Q1+Q2
- severity: note
- coverage: `no_recorded_issue`
- failing scenario: everything a program needs about how the turn was
  resolved - the `provenance:` lines, the `divergence:` lines, the
  `spawn:` line - is written to stderr only, in both render modes, by
  design ("stdout carries the NDJSON contract"). A consumer reading only

  `kill-1.ndjson` carries none of that information.

  plans for two streams per turn. If it were to change, the carrier would
  be an added `HarnessEvent` kind, which is D4's call, not D1's.

## Gaps

- Criterion 1, second clause ("token lines span more than one second") is
  not decidable from the permitted D11 prompt: `Reply with only: alpha`
  produces two token events on claude, one on pi, one on muse, so the span
  is 0.13 s, 0 s and 0 s. Real-time delivery is proven another way for
  claude (11 events readable in `kill-1.ndjson` while the child ran on) and
  for muse (its token line arrived 1.79 s before its `done` line). For pi
  the only margin is 47 ms between `token` and `done`, which is consistent
  with streaming but does not prove it. The delivery path is shared code
  with no per-harness buffering (`run.ts:455-471` writes each event through
  `writeEventNdjson`, one `process.stdout.write` per event), so I record
  criterion 1 as pass and this as thin evidence on pi only.
- Criterion 3, codex sub-clause ("codex's new thread id is reported in
  turn 2's identity") is unproven. The only permitted codex resume was
  D8's `question-roundtrip`, which exempts codex from the identity check
  and records no ids (F-D1-4). Statically the path works -
  `freshDecodeState` (`decode.ts:22-26`) starts `lastSeenId: null` and
  codex's `harness-minted` authority skips the rotation guard at
  `identity.ts:70-76`, so whatever id codex announces on turn 2 is emitted
  as an identity event - but whether codex mints a new thread id on
  `exec resume` was not observed.
- Whether the killed claude child was reaped promptly or only at the
  grace-expiry SIGKILL is not separable from the measurement: the
  uncancelled 5 s timer in `run.ts:432-441` sets a floor of 5 s on `hcn`'s
  own exit regardless. The child's exit code 143 says it died of SIGTERM,
  not SIGKILL.
