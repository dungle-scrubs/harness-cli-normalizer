## Findings

### F-D4-1 `src/interpretation/argv.ts:147`

- question: Q1+Q2
- severity: blocker
- coverage: read directly with the Read tool; `check_index_coverage` not run
  on `argv.ts`/`session-id.ts` because they are cited only through this
  finding - both were read in full at the cited ranges
- failing scenario: a caller resumes with a session id that fails the shape
  rule - a leftover `-`-leading token, a truncated id, an id read from a
  crashed transcript. `buildResumeArgv` calls `assertUsableSessionId`, which
  throws `SessionIdRefusalError`. That class does not extend
  `ArgvRefusalError`, so `stream-turn.ts:187-218` rethrows it at `:217`,
  before the `try` at `:477`. The generator throws out of its first `next()`
  and emits zero events - no `failure`, no `done`. `README.md:208` states
  the opposite: `streamTurn` "never throws out of its first `next()`". A
  reducer awaiting `done` for the turn it started never gets one, and the
  CLI's rescue at `run.ts:489-500` relabels the refusal as
  `class: "transport", retryable: true`, so a router walks its fallback
  chain re-sending the same malformed id to every model.
- evidence: `node SCRATCH/audit/d4/probe-resume-id.mjs` ->
  `{"resume":"--dangerously-skip-permissions","events":[],"thrown":"SessionIdRefusalError: ..."}`
  and the same for `"../../etc/passwd"`. `buildSessionArgv` at `argv.ts:177`
  has the identical hole.
- smallest change that flips it to pass: make `SessionIdRefusalError`
  (`src/interpretation/session-id.ts:24`) an `ArgvRefusalError` with issue
  `invalid-option-value`, or catch it beside `ArgvRefusalError` in
  `streamTurn`'s `catch` at `stream-turn.ts:188` so the existing
  `failureFromRejected` + `done` path runs.

### F-D4-6 `src/execution/failure.ts:99`

- question: Q1
- severity: major
- coverage: `no_recorded_issue`
- failing scenario: the harness binary is not installed on the box - the
  single most common Q1 failure for a wrapper agent that routes to codex,
  pi, or muse. Node reports ENOENT asynchronously, so `node-deps.ts:140-142`
  resolves `exited` with 127 and pushes the message onto stderr rather than
  throwing synchronously. `stream-turn.ts:486-498` then sees a nonzero exit
  with a non-empty stderr tail and classifies it `failureFromNative`:
  `retryable: false`, `done.exitCode: null`, `cause: "crash"`, message
  "NATIVE ERROR from harness ... the harness rejected or failed on its own
  arguments". A router obeying `retryable: false` stops instead of falling
  back to a harness that is installed, and the message blames a harness that
  never ran. `runner-hardening.test.ts:274` pins the opposite classification
  (`transport`, `exitCode: 127`, `cause: "failed"`) but drives a fake
  spawner that throws synchronously - a path the shipped adapter never
  takes.
- evidence: `node SCRATCH/audit/d4/probe-enoent.mjs` with real
  `nodeRunnerDeps` ->
  `{"kind":"failure","class":"native","retryable":false,...,"nativeExitCode":127}`
  then `{"kind":"done","exitCode":null,"cause":"crash","failure":{...native...}}`.
- smallest change that flips it to pass: in `node-deps.ts` mark the async
  spawn error distinctly (the adapter already holds `spawnError` at
  `:141`), and in `stream-turn.ts:493-497` classify an exit whose stderr
  tail is that spawn error as `failureFromTransport`, not
  `failureFromNative`.
