## Findings

### F-D7-1 `src/interpretation/argv.ts:178-185`

- question: Q2
- severity: major (session mode is outside the readiness gate; the same
  function is the only session-argv builder, so it is not cosmetic)
- coverage: `no_recorded_issue`
- failing scenario: `buildSessionArgv` unconditionally prepends
  `h.launch.baseFlags` before `h.sessionMode.flags`. For pi, `baseFlags` are
  the ONE-SHOT turn flags `["-p","--mode","json"]` (`pi.ts:22`), so
  `hcn session pi` spawns `pi -p --mode json --mode rpc` - `--mode` twice with
  conflicting values, plus `-p` (print/one-shot) on a process that is supposed
  to hold a bidirectional rpc session. The verified invocation in the spike
  that the descriptor cites is `pi --mode rpc` with neither flag
  (`test/fixtures/pi-rpc-spike/spike.py:87`). `descriptor.ts:258-259` calls
  `sessionMode.flags` "the exact flag set that opens one lucid-owned process",
  which the builder contradicts.
- evidence: library probe output -
  `pi session argv   : ["pi","-p","--mode","json","--mode","rpc"]`
  (`SCRATCH/audit/d7-lib-probe.mjs`). claude is unaffected: its `baseFlags`
  are `["-p"]`, which claude's session mode needs. No test catches it -
  `test/execution/session-questions.test.ts:163-165` asserts only
  `toContain("--mode")`, `toContain("rpc")`, `not.toContain("--session")`.
- smallest change that flips it to pass: give `sessionMode` its own base-flag
  set, or have `buildSessionArgv` in `src/interpretation/argv.ts` skip
  `h.launch.baseFlags` and read the full argv prefix from
  `h.sessionMode.flags`; then pin the whole argv (not `toContain`) in
  `test/execution/session-questions.test.ts`.

### F-D7-2 `src/knowledge/descriptor.ts:256` / `src/execution/stream-turn.ts:258`

- question: Q1+Q2
- severity: major
- coverage: `no_recorded_issue` on both
- failing scenario: `resume.onMissing` is `"create"` for pi and muse
  (`pi.ts:37`, `muse.ts:38`) and its own doc comment warns that "a consumer
  resuming a session it believes exists gets a blank session, not an error".
  Nothing in `src/` reads the field - `grep -rn 'onMissing' src/` hits only the
  descriptors and the type. So `hcn run pi --resume <stale-or-typo-uuid>` runs
  a fresh, historyless session; the harness announces the requested id, so
  `decodeIdentity` returns `announced` (not `rotated`) and the stream carries
  a normal `identity` + clean `done`. lucid-v2's turn strategy
  (`lucid-v2/src/modes/host.ts:127,167,184`) feeds `resumeId` back per turn and
  has no way to see that the context was dropped.
- evidence: `grep -rn 'onMissing' src/ test/ scripts/ README.md` returns
  descriptor lines plus `test/knowledge/harnesses.test.ts:249-252` (which only
  asserts the values); `src/execution/stream-turn.ts:258`
  (`freshDecodeState(effective.resume ?? null)`) and
  `src/interpretation/identity.ts:70-80` show rotation is the only anomaly the
  runner detects.
- smallest change that flips it to pass: in `src/execution/stream-turn.ts`,
  when `effective.resume` is set and `h.resume.onMissing === "create"`, emit a
  warning `error` event (or a dedicated field on the `identity` event) naming
  the create-on-missing risk, and document it under `--resume` in
  `src/cli/help.ts` `RUN_HELP`.

### F-D7-3 `src/knowledge/pi.ts:47-56`

- question: Q2
- severity: major
- coverage: `no_recorded_issue`
- failing scenario: pi's session mode has `idFlag: null`, so the session id is
  minted by pi and read only through the `get_state` probe
  (`open-session.ts:283-334`). Criterion 3 requires that this minted id then
  resumes through the turn path, `hcn run pi --resume <id>` (which spells the
  id as `--session-id` under `-p --mode json`). No test, fixture, or captured
  run shows an rpc-minted id being re-entered from turn mode. The spike README
  says `--session <id>` re-enters in RPC mode, which is a different flag in a
  different mode. If the two namespaces differ, a lucid-v2 flow that opens a pi
  session, reads the identity, closes, and resumes gets a blank session
  (compounded by F-D7-2's silent create).
- evidence: `test/fixtures/pi-rpc-spike/assertions.txt` (25 assertions, none
  about turn-mode resume); `test/fixtures/pi-rpc-spike/README.md` "Implications"
  paragraph; no `test/**` reference to a pi session-to-turn resume.
- smallest change that flips it to pass: capture one live probe - open
  `pi --mode rpc`, read `get_state`'s `sessionId`, close, then run
  `pi --session-id <that id> -p --mode json "<recall prompt>"` - store it under
  `test/fixtures/pi-rpc-spike/` and record the result in the `resume` comment
  block of `src/knowledge/pi.ts`.

### F-D7-4 `src/cli/inspect.ts:186` vs `src/cli/run.ts:332-337`

- question: Q1
- severity: major
- coverage: `no_recorded_issue` on both
- failing scenario: `hcn run <h> --resume <id>` skips turn-option resolution
  (`run.ts:240` gates `resolveEffectiveOptions` on `extra.resume === undefined`)

  run would succeed. An agent using `inspect --argv` to check a resume before
  spending a turn is told codex resume is impossible.
- evidence: `node dist/cli.js inspect claude --argv --session-id <uuid>
  --prompt hi` prints
  `["claude","--resume",<uuid>,"-p","--effort","high",...]` - `--effort` comes
  from profile resolution, which `run.ts` skips on resume. Same command for
  codex prints `"sandbox" cannot be expressed on resume for codex; supported:
  effort, systemPrompt` and exits 2.
- smallest change that flips it to pass: in `src/cli/inspect.ts`, build the
  resume preview from the unresolved `turnOpts` on the `values.resume`
  branch, mirroring `run.ts`'s launch-only rule.
