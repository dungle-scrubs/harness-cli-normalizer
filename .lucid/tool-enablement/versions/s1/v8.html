Two facts shape everything below. First: pi's default toolset is not "all tools" - grep, find, and ls exist but are off unless granted. So "everything except X" has two possible meanings and D3 settles which. Second: claude is the only harness with pattern syntax, so patterns cannot be part of the normalized vocabulary.

D1 - List semantics

How --tools and --exclude-tools combine. Only claude and pi can express lists at all; on codex and muse the whole dimension is not-applicable and follows the tier rule from the defaults discussion (built-in skips, config refuses, args refuse).

A - Mutually exclusive pairrecommended

One list per call. Include means exact allowlist. Exclude means everything else.

  • Passing both refuses with exit 2
  • Empty include --tools "" = no tools; already works this way
  • Maps 1:1 onto both CLIs that support lists

B - Composable, exclude wins

Claude's native model: allow a set, then carve out of it.

  • More expressive for wide-grant-minus-one cases
  • Pi accepting both flags at once is unverified - grounding needed
  • Two interacting lists make config merging and provenance harder

C - Include only

Drop exclude from the normalized surface.

  • Smallest surface
  • "All except the dangerous one" must enumerate every safe tool
  • Breaks when a harness adds a new tool - the enumeration goes stale

D1

Adopt A: --tools and --exclude-tools are mutually exclusive per call; include is an exact allowlist, exclude is the complement. Agree, or pick B or C?

D2 - What "everything" means

Only matters when exclude is used. Pi ships 7 built-ins but enables 4 by default. The two meanings diverge there.

Harness default, minus exclusions

Exclude starts from what the harness would run anyway.

  • On pi, --exclude-tools bash leaves read, edit, write - grep, find, ls stay off
  • Never widens a run beyond its default
  • "Exclude" behaves as a pure subtraction

All known names, minus exclusionsrecommended

Exclude starts from every tool in the descriptor, stamped to the version.

  • On pi, --exclude-tools bash leaves read, edit, write, grep, find, ls
  • Same mental model on every harness
  • Can widen a run past the harness default - pi gains grep, find, ls

D2

When rendering an exclude, start from all names known to the descriptor (pi would gain its three off-by-default tools), or from the harness default (pure subtraction)?

D3 - Tool vocabulary

Tool names are not shared across harnesses. The normalized CLI needs one vocabulary; the descriptors hold the per-harness mapping, stamped to verifiedAgainst.

A - Normalized names, mapped per descriptorrecommended

A curated set in the vocabulary layer; each descriptor carries its spelling.

  • read, bash, edit, write, grep, find, ls - pi spells them exactly this way today
  • Claude's capitalizations map case-insensitively or via a table
  • Extensible rule (from review): extension and custom tools register at runtime, unknowable at descriptor time. The vocabulary is extensible exactly like pi's model registry - curated names validate and map; unknown clean names (selector shape) pass through and are carried in provenance. Closed refusal applies only to the curated set's typos
  • pi's --tools/--exclude-tools govern built-in, extension, and custom tools together - one surface covers all three populations

B - Pass-through names

Send the string as given; each harness judges it.

  • Zero mapping to maintain
  • Same script needs different names per harness - defeats the point
  • Typo protection is lost; claude silently ignores unknown names

C - Normalized core + pattern escape

Normalized names, plus claude-only pattern tokens passed through.

  • Keeps Bash(git *) reachable for claude users
  • Patterns refuse on pi - a per-harness branch inside one flag
  • Defer until someone needs it; A does not block adding it later

D3 - decided

Adopt A: curated normalized name set, per-descriptor mapping, extensible rule for runtime-registered tools - curated names validate and map, unknown clean names pass through into provenance. Patterns stay claude-only and out of scope for now. Confirmed in review.

D4 - Skills granularity

Per-skill include exists in exactly one harness, and it is additive-by-path, not selection-by-name. Skills selection is also load-bearing for hcn's own operation: skills decide how a delegated run behaves.

A - Facet on/off onlyrecommended

Normalize what more than one harness shares: skills enabled or disabled per call.

  • pi -ns, claude --setting-sources; codex and muse are not-applicable
  • Fits the existing discovery facet table and its tier rules
  • Per-skill selection stays out of the normalized surface

B - Add per-skill include

Surface --skill in the normalized CLI.

  • pi-only; refusing on three of four harnesses
  • Takes a path, not a name - it is a load instruction, not a selection
  • Overlaps the config-tier story: a skills list in config covers this need better

D4

Skills stay a discovery facet (on/off per call, per config tier), with no per-skill selection in the normalized CLI. Agree?

D5 - Config interplay

Tool sets are the first dimension where a user will want named bundles, because they repeat across calls: a review run wants the read-only set.

A - Named toolsets in configrecommended

Config tiers can define toolsets: a name plus a list, in the normalized vocabulary.

  • toolsets: { review: [read, grep, find, ls] }
  • CLI references it: --tools review - a bare name that matches a toolset resolves to it
  • Project tier "turn off everything" sets the floor toolset []; args can only grant within it... or replace it - needs one more rule below

B - Inline lists only

No names; every call spells the list.

  • No new config schema
  • Repetitive; long command lines
  • The all-off project tier still needs a floor-toolset concept anyway

D5

Two parts. First: config defines named toolsets and the CLI can reference one by bare name. Second: when a project config sets a floor toolset, an explicit --tools arg must not grant tools outside it (floor wins), or the arg replaces the floor for that call (arg wins)? Recommendation: floor wins.

D6 - Native passthrough and error labeling

Decided in review: the normalized surface covers what is shared; everything else reaches the harness through an explicit passthrough. Partial normalization is accepted as long as native failures read as native.

A - -- separatordecided

Everything before -- is hcn's normalized surface and refuses unknown flags. Everything after -- passes to the harness verbatim.

  • A wrong-harness flag fails in the harness itself, loudly - all four error on unknown flags at exec time
  • Zero new descriptor data required
  • Descriptor-validated passthrough stays available as later work

B - Native error labelingdecided

A passthrough failure is labeled native, never presented as an hcn error.

  • Event stream carries the harness stderr verbatim under a distinct native failure class
  • Exit codes stay split: 2 for hcn refusals, 1 for native failures
  • Rendering prefixes native output so the two cannot be confused

D6

Recorded as decided: -- passthrough separator, native failures labeled as native and kept distinct from hcn refusals, partial normalization accepted (tools vs capability categories stay distinguishable, not flattened). Confirm to close, or annotate.

D7 - Cross-harness refusal diagnostics

Decided in review: a refusal caused by a harness lacking a dimension should say which harnesses do support it. One reusable pattern, two refusal classes.

A - Support list on refusaldecided

When an option is refused because the target harness lacks it, the refusal lists every harness that has it, with its native spelling.

  • --tools on codex: tools is not available on codex; supported on: claude (--allowedTools)
  • Derived from descriptors at runtime, never hardcoded strings
  • Existing precedent: the autonomy refusal already lists per-harness flags - but as a hardcoded array, which is the drift pattern to avoid when generalizing

B - Native spelling recognitiondecided

When a native flag is passed before --, the unknown-flag error recognizes it and redirects to the normalized surface.

  • --allowedTools on codex: unknown flag; --allowedTools is claude's spelling - use --tools (supported on: claude)
  • Mapping lives in descriptor data (each dimension's native spellings), stamped to verifiedAgainst
  • Unrecognized natives keep the plain unknown-flag refusal

D7

Recorded as decided: unsupported-option refusals carry a cross-harness support list derived from descriptors; known native spellings get recognized and redirected to the normalized flag. Confirm to close, or annotate.

D8 - Refusal hints that keep the caller on its harness

Decided in review: a support list alone can induce a caller to switch harnesses for a feature. The refusal should first suggest the nearest capability on the harness already chosen.

A - Hint first, support list lastdecided

Refusal message order: statement, then the stay-on-harness hint, then the cross-harness support list.

  • tools is not available on codex. Nearest control on codex: category switches (--enable/--disable <FEATURE>) or sandbox modes. Supported on: claude (--allowedTools).
  • A scanning caller hits the stay suggestion before the switch temptation
  • Hints are curatorial data per dimension per harness, stamped to verifiedAgainst - not mechanically derivable

B - Structured fields in the eventdecided

The refusal event carries hint and supportedBy as separate fields, so programmatic callers choose deliberately instead of pattern-matching prose.

  • JSON mode renders both as data
  • Human rendering keeps the ordered prose from A

D8

Recorded as decided: refusals lead with a nearest-alternative hint for the current harness, keep the support list as secondary data, and expose both as structured event fields. Confirm to close, or annotate.
