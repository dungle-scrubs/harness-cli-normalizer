hcn defaults roadmap

Next five dimensions, one decision each

Five ratification proposals in the order they should land. Each card: the facts, the proposal, and the decision you owe. D-numbers continue from the tool-enablement review (D1-D8 closed).

Ordered by cost/benefit: two free ratifications, one new dimension, one behavior change, one design sitting. Model abstention recorded at the end.

D9 - write: true

Muse-only toggle. True emits nothing on claude/codex/pi and omits --disable-write on muse - the emit-nothing rule from the autonomy ratification applies directly.

Proposal write: true in the profile. Provenance answers "can a bare run modify files?" - write = true (profile) - and muse's bare runs stay exactly as they are today.

D9: ratify write = true?

Zero behavior change on any harness. One card with D10 - same shape, same PR.

D10 - shell: true

Identical shape: muse-only, true emits nothing elsewhere. Completes the "what can this run do to my machine" row of provenance.

Proposal shell: true alongside D9. Together: provenance shows write = true, shell = true on every bare run, every harness.

D10: ratify shell = true?

Same zero-cost shape as D9. The honest question is whether you want the DEFAULT to be permissive - but that is already today's behavior on all four; this only names it.

D11 - timeout: a new dimension hcn owns

Not a harness flag. hcn owns the process and already has the machinery: the injected { spawn, clock, signal } adapter, the stall watchdog, and the kill-grace ladder in streamTurn.

  • Identical semantics on all four harnesses - no descriptor data, no divergence column, the only fully-uniform dimension possible
  • Max-steps and sandbox hints already tell callers to "impose a wall-clock timeout at the caller" - this makes hcn that caller
  • Mechanics: deadline via clock, SIGTERM then SIGKILL after grace, done cause: "killed" with a timeout failure class (or reuse "budget")
  • --timeout <seconds> arg; config tier key "timeout"; profile default needs your number
Proposal New dimension, implemented in the execution layer. Profile default 600s: long enough that no legitimate turn trips it, short enough that a runaway loop dies in 10 minutes instead of overnight. Your number overrides.

D11: add the timeout dimension, default 600s?

Also decide: unlimited opt-out (--timeout 0 or --no-timeout) - recommend explicit --timeout 0, zero being "disable" follows the config tier's delete semantics.

Cost: execution-layer change, e2e scenario with a deliberately-hanging prompt, ~one sitting including tests.

D12 - maxSteps: the first deliberate behavior change

Muse-only (--max-model-steps, 1-10000, currently unbounded on bare runs). The other three report divergence - correct, visible, and the hints already route callers to prompt-bounds or timeouts.

  • Muse exits 1 on step exhaustion with a distinct budget-vs-task split (descriptor's A-003 note)
  • A default turns muse's infinite loop into a bounded, classified failure
  • On claude/codex/pi: divergence lines name the dimension; timeout (D11) becomes the real backstop there
Proposal Profile default 200 steps for muse. High enough that normal tasks never see it (a step is a model call with tools, not a token), low enough that a stuck agent dies in minutes. Needs one live probe of muse's exhaustion behavior before shipping to pin the event mapping.

D12: ratify maxSteps = 200 (muse-only)?

Your number. 500 and 1000 are defensible; 200 is my recommendation because the failure mode it guards (silent runaway) costs more than a spurious stop.

Cost: one probe, resolver entry, divergence plumbing (already built), e2e scenario.

D13 - tools: the heavyweight, last on purpose

A profile-level default grant answers "what does a bare run get?" uniformly. It changes behavior on every harness and needs its own design sitting - this card scopes it, ratification comes later.

  • Open questions: does the profile default interact with project floors (a floor tighter than the profile default - who wins?), does pi's off-by-default grep/find/ls become on-by-default under hcn, does claude's everything-on stance get narrowed?
  • The floor rule (D5) already exists; profile-vs-floor precedence is the new rule needed
  • Arguments/config tiers all flow through existing machinery - this is curation plus one precedence rule, not new mechanics
Proposal Defer ratification. Land D9-D12 first; schedule the tools design as its own lucid sitting with the pi/claude asymmetries on the table. My leaning when it comes: profile grants nothing by default (all tools stay available per harness default), because the project tier already provides "less by default" where wanted - but that is for the sitting.

D13: defer tools ratification to its own sitting?

Agreeing to defer is the decision. If you would rather pull it forward, D11 and D12 slide.

Model: ratify permanent abstention

Not one of the five - a closure. No shared model namespace exists across harnesses; pi's registry is runtime-extensible and environment-dependent; per-harness config already covers "claude on X, pi on Y."

Proposal Record in the profile's doc comment and the README: model is permanently out of profile scope. The dimension stays arg-only and config-only. Closes the question rather than leaving it open.
