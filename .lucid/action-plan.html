hcn implementation plan

Sequence: defaults, tool enablement, config tiers

Eight phases, each ending at a runtime gate. Nothing that changes spawn behavior lands until the gate before it is green. Ordering follows one rule: evidence before data, data before rendering, rendering before policy, policy before configuration.

Carries: defaults profile (user config, project config, args) · tool decisions D1-D8 · structured-first events · provenance · CLI-only stance

The gate, defined once

You asked for E2E runtime testing between every item. This is what the gate checks at every phase boundary, so "done" means the same thing each time.

Every phase ends with all of: (1) pnpm check green - lint, typecheck, both test lanes; (2) the E2E scenario suite green against live harnesses (Phase 0 builds it, each phase adds its scenarios); (3) when facts were verified or re-verified: fixtures committed and verifiedAgainst bumped with smoke:seven re-run; (4) when option resolution changed: hcn inspect output updated with provenance.

The sequence

0Grounding and the E2E rig

Nothing changes behavior. This phase buys the evidence and the instrument that makes every later gate meaningful.

  • Capture bare-run evidence per harness as fixtures: what effort actually runs, which tools are active, discovery state - the "harness decides" column of the defaults matrix, made factual
  • Close the four open questions: claude --disallowedTools interplay and --disable-slash-commands semantics; codex config.toml tool keys; pi --tools + --exclude-tools together; muse flags one at a time
  • Build scripts/e2e: a scenario runner that drives hcn run against real harnesses and asserts on NDJSON events, exit codes, stderr - baseline scenario: bare run per harness decodes and exits clean
E2E gate - baseline suite green on all four harnesses; evidence fixtures committed.

1Descriptor tool data

Pure data, no rendering. Every later tool behavior reads these facts.

  • New tools field per descriptor: curated names, default-enabled state, native flag spellings, category switches as recorded facts
  • Grounded strictly in Phase 0 fixtures - no entry without evidence
E2E gate - inspect prints the per-harness tool table; vocabulary unit tests pass; argv output unchanged.

2Tool selection surface

D1, D2, D3 become real: the first behavior change, kept small by landing before diagnostics and policy.

  • --tools and --exclude-tools: mutual exclusion refusal (structured), curated mapping, extensible pass-through with provenance marker for unmapped names
  • Pi exclude rendered as computed include list (D2); claude via allow/disallow flags
E2E gate - live scenarios: pi granted read-only refuses a bash task; claude grant changes tool behavior; codex/muse refuse --tools with the plain refusal (diagnostics come next).

3Refusal diagnostics and hints

D7, D8, and the structured-first rule. The 25 curatorial confirmations interleave here - one hint shipped, one confirmed by you, repeat.

  • Event shape v2: refusals as data first - hint, supportedBy, conflict fields
  • Support lists derived from descriptors at runtime; native spelling recognition with redirect
  • Hint mechanism seeded with the first confirmed instances; remaining 22 land on your confirmation cadence
E2E gate - every refusal class triggered and asserted field-by-field; golden snapshots of refusal events.

4Passthrough and native error labeling

D6. Small, isolated, and it hardens the failure path before defaults multiply the number of runs.

  • -- separator end to end: normalized surface before, verbatim after
  • Native failure class: harness stderr verbatim, labeled, native exit code as data, hcn exit 1
E2E gate - wrong-harness flag after -- on codex surfaces the native error labeled; before -- it is recognized and redirected; exit codes assert 1 vs 2.

5Defaults profile - the built-in tier

The headline feature, deliberately after the rig, the tool surface, and the failure path are all proven.

  • DEFAULT_TURN_PROFILE in knowledge: effort medium, codex sandbox workspace-write, discovery on, autonomy off - each dimension ratified one at a time with you first
  • The resolver: resolveEffectiveTurnOptions, launch-only application, skip-and-report for unrenderable dimensions
  • Provenance becomes visible: inspect shows each dimension's value and tier
E2E gate - bare-run argv snapshots updated per profile; live runs verify effort medium takes effect per harness (stream evidence); pi's missing sandbox shows as reported divergence, not silence.

6Config tiers - user and project

Built on the resolver from Phase 5; keys mirror the now-stable arg surface.

  • Schema + parser with hard-fail on unknown keys, malformed values, schema version mismatch - exit 2, never warn-and-skip
  • User config, then project config, per the ratified precedence and merge semantics
  • Named toolsets and the floor rule (D5): grant exceeding floor is a structured refusal naming both sets
  • Project-config discovery per the trust decision you ratify below
E2E gate - temp-dir config scenarios: override applies, floor refuses, bad config exits 2 with the offending key named.

7CLI-only surface

Mechanical, and last so the public surface is stripped once, after features stabilize.

  • Remove library subpath exports from package.json; major version bump
  • README rewritten: the normalizer now normalizes the interface and the defaults, with divergence reported - the "facts, not configuration" stance updated to say so
E2E gate - full suite; npm pack contains no unintended surface; install-from-tarball smoke test passes.

Ordering decisions to confirm

Four places where the sequence could run differently. My recommendation in each; override any.

P1 - tools surface before defaults profile

Recommended: yes, as sequenced. Defaults change every bare run at once, so they want the mature gate; toolsets and the floor rule (config, Phase 6) also depend on tool rendering existing. Alternative: defaults right after Phase 0 because they are the headline want - accepted cost: profile changes land before the failure path (Phase 4) is hardened.

P2 - E2E gate scope per phase

Recommended: all four harnesses at every gate for argv/refusal/config phases; for spawn-cost scenarios (real model turns), claude + pi every gate with codex + muse on every second gate and always pre-release. Alternative: all four at every gate, no rotation - slower and costs more, maximum rigor.

P3 - when to ratify each default

Recommended: the per-dimension confirmations (effort medium, sandbox value, discovery, autonomy) happen during Phase 5 implementation, one dimension per sitting, same cadence as the 25 hints in Phase 3. Alternative: ratify the whole profile up front at Phase 5 start.

P4 - project-config trust model

Recommended: auto-discover at the git root, but a project config that tightens nothing and only widens (raises effort, grants tools) requires --project-config opt-in on first encounter per repo. Alternative A: always auto-discover (AGENTS.md precedent). Alternative B: always explicit opt-in (safest, most friction).

What runs alongside, not in sequence

  • The 25 hint confirmations - your cadence, interleaved with Phase 3
  • Per-dimension default ratifications - interleaved with Phase 5 (P3)
  • Provenance grows at Phases 2, 5, 6 as each adds something to report
  • Fixture capture and verifiedAgainst discipline - continuous, per repo convention
