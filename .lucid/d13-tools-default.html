Tools default and the equivalence principle

Your lean: harnesses equivalent as possible by default. This sitting maps every tool-surface asymmetry onto that principle, ratifies the first profile tools entry, and fixes the rules future dimensions follow.

Probe on record: pi's dormant trio enables via include and works (grep executed a real search, correct file:line, 2026-08-19).

The principle

Equivalence wherever expressible; divergence only where structural When a harness CAN match the others' default behavior - the capability exists and is one flag away - the profile makes it so. When the harness has no surface at all (codex/muse tool lists), nothing can be normalized and divergence is reported, not papered over. Dormancy is a choice, not a gap: pi's off-by-default trio is expressible and therefore becomes equivalent.

The standing cost, accepted: a small prompt-token tax on every pi bare run (three more tool schemas) in exchange for meaning the same thing as the other harnesses. Callers wanting pi lean override with --tools; provenance records the arg.

The proposed profile entry

tools: full known set, per harness Profile gains tools rendered per harness from descriptor data: on pi, the include list enabling all seven built-ins (the dormant trio turns on); on claude, emit nothing - its default is already everything, and an include there would trigger the deny-complement rendering, changing argv for zero semantic gain; on codex/muse, skip-and-report divergence (no list surface). Provenance shows tools = "all known" (profile) everywhere.

Implementation shape: the entry is a marker ("all-known"), not a literal list - the resolver expands it against each descriptor so new harness tools flow in without profile edits. The floor interaction (your earlier question): a project floor tighter than the profile is a deliberate narrowing and wins - the floor rule already refuses arg grants outside it, and the profile entry composes the same way (project config overrides profile per the precedence chain).
